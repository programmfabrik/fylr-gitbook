## Important

* **A file that is not the format its name says fails.** A file whose content does not match its extension, such as a TIFF without its TIFF header, is marked failed when it is uploaded and gets no renditions. Such a file uploaded before the update is marked failed at its next resync, for example from `/inspect/files/`, and its renditions are removed. See "A damaged TIFF no longer blocks the file worker" under **Fixed**. [2bd4b7b85] [65e6af635]

* **Renditions of files from 6.34 are kept.** 6.35.0 and 6.35.1 produce the image renditions and the `pages` version of such a file again when the file is synced, for example by a resync of the originals or by saving a record. 6.35.2 keeps the existing renditions. See "Renditions of files from 6.34 are kept" under **Fixed**. [e75082294]

## fylr core

### Fixed

#### A damaged TIFF no longer blocks the file worker

The renditions of a TIFF that cannot be read were produced without end: each one kept an execserver slot, also after a restart of fylr, and every such file slowed down the production of all other files. Such a TIFF fails now. A file whose content is not the format its name says, such as a TIFF without its header, is marked failed when it is uploaded and gets no renditions; the renditions of another unreadable TIFF are marked failed. A resync of a failed original reads the file again instead of producing its renditions. [2bd4b7b85] [65e6af635]

#### Renditions of files from 6.34 are kept

In 6.35.0 and 6.35.1, the sync of a file from 6.34 produced its image renditions and the `pages` version of its documents again, although their configuration had not changed. A resync of all originals did this for every file, and saving a record did it for the files of the record. Until a new rendition was done, the file had no preview. The sync now keeps a rendition produced from the same source with the same recipe, params, source version and custom metadata. Renditions with a watermark, a caption or a color profile uploaded to the base config are still produced again. [e75082294]

## Web frontend

### Fixed

* An export with *Export files & data from linked records* turned off no longer fails with *The search field "…" is unknown* or writes a CSV without columns: the fields and files picked for linked records stayed in the export, although the export dialog no longer showed them. An export of selected records with the option turned off also keeps the files of the records themselves, such as those of a reverse linked record. [f198d26c6]
