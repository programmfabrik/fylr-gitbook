# Release v6.35.2

{% hint style="warning" %}
**Not released yet.** These notes describe fixes for 6.35 that have not
shipped: there is no `v6.35.2` tag, no build and no Docker image. Contents and
wording can still change before the release.
{% endhint %}

## Important

* **A file that is not the format its name says fails.** A file whose content does not match its extension, such as a TIFF without its TIFF header, is marked failed when it is uploaded and gets no renditions. Such a file uploaded before the update is marked failed at its next resync, for example from `/inspect/files/`, and its renditions are removed. See "A damaged TIFF no longer blocks the file worker" under **Fixed**. [2bd4b7b85] [65e6af635]

* **An update from 6.34 keeps the renditions whose configuration did not change.** 6.35.0 and 6.35.1 produce the image renditions and the `pages` version of the documents of a file from 6.34 again at its next sync, for example after a resync of all originals or when one of its records is saved. 6.35.2 keeps them. Renditions that 6.35.0 or 6.35.1 already produced again, or queued to be produced again, are not brought back. See "An update no longer produces unchanged renditions again" under **Fixed**. [e75082294]

## fylr core

### Fixed

#### A damaged TIFF no longer blocks the file worker

The renditions of a TIFF that cannot be read were produced without end: each one kept an execserver slot, also after a restart of fylr, and every such file slowed down the production of all other files. Such a TIFF fails now. A file whose content is not the format its name says, such as a TIFF without its header, is marked failed when it is uploaded and gets no renditions; the renditions of another unreadable TIFF are marked failed. A resync of a failed original reads the file again instead of producing its renditions. [2bd4b7b85] [65e6af635]

#### An update no longer produces unchanged renditions again

After an update from 6.34, the next sync of a file produced its image renditions and the `pages` version of its documents again, although their configuration had not changed and almost all of them came out exactly as before. A resync of all originals queued all of them, and saving a record did the same for its files. A rendition produced from the same source with the same recipe, params, source version and custom metadata is kept now. A rendition with a watermark or caption, or with a color profile uploaded to the base config, is produced again as before, and so is a rendition a resync selects itself. [e75082294]
