# Release v6.35.0

{% hint style="warning" %}
**Not released yet.** These notes describe work that has landed on `main` but has
not shipped: there is no `v6.35.0` tag, no build and no Docker image. Contents and
wording can still change before the release.
{% endhint %}

## Server

### Important

* **This release forces a blocking re-index.** Existing cached standards and
  search documents are rebuilt to include complete linked and reverse-linked
  content. Only `/inspect/` is available while it runs; allow time for the
  database upgrade and re-index on large installations. See **Recursive
  standards and indexing** under **Fixed**. [4a26c76c3]

* **A proxy in front of fylr has to be declared: `fylr.trustProxyHeaders`.**
  fylr takes the client's address from the connection it is talking to. Where
  something in front of fylr forwards the client identity — `x-real-ip`, or
  `x-forwarded-for` — that identity is used only when
  `fylr.trustProxyHeaders` is on, which says fylr is reached **only** through
  such a proxy. It is **off by default**.

  A proxy on the same host needs no change: a request arriving from loopback is
  always believed, and so is fylr's own internal hop between listeners. **A
  proxy anywhere else — a container network, another host, a Kubernetes
  ingress — needs the setting turned on, or every request looks like it came
  from that proxy**: users lose the groups an IP subnet filter grants them (a
  filter set to exclude puts them in the opposite group instead), the
  failed-login lockout counts all users against one address, and the audit log
  records the proxy. fylr logs a warning naming the peer, once an hour, when a
  request carries one of those headers while the setting is off, so the case is
  visible in the log.

  Leave it off where fylr can also be reached directly: the setting decides
  whether fylr lets a caller name the address that its IP-filtered group
  membership, its lockout counter and its audit entries are keyed on.
  [193b673297]

* **Restore needs a backup taken with 6.35.0 or newer**: `fylr restore` reads a
  backup's payloads as the version that wrote them left them, and no longer
  carries fallbacks for older shapes. It now checks the backup's fylr version
  up front and refuses an older one before it touches the target, naming the
  version it found. Take a fresh backup of the source with a current fylr
  instead of restoring an old one. [4c58c62fb]

* **Execservers now use a fylr-initiated broker protocol, and execserver and
  fylr must be upgraded together.** The previous polling transport (an HTTP
  `PUT` carrying a job token) is removed — fylr opens a websocket to each
  execserver and pushes jobs onto free slots. An execserver without a broker
  connection to fylr receives no work, and an old/new version mismatch on
  either side exchanges no jobs, so plan the upgrade to move both sides
  together.

* **The upgrade runs a blocking schema migration (198)** that rebuilds the file
  uniqueness index.

* **Execserver concurrency and addressing configuration changed.** `parallel`
  and `parallelHigh`, and the default per-service `waitgroup` assignments, are
  gone — concurrency is auto-balanced now (see *Improved* below), though an
  explicit `waitgroups` block still works. `tokenResponseSendServerIP` is
  removed: fylr auto-detects the address an execserver reaches it back on from
  the broker connection, and the new optional `callbackBackendOwnURL` overrides
  that only for NAT topologies where the detected address is not directly
  reachable. `callbackBackendInternalURL` and `callbackApiInternalURL` are no
  longer required and no longer supply the HOST — they still override scheme
  and port, for a proxy in front of the listener, but the host is always this
  fylr's own. A Kubernetes Service name in either of them therefore has no
  effect; that was never a working configuration, because the pipe and
  `api_tx_url` callbacks must reach the exact replica that created the job,
  and it now fails visibly instead of silently landing on a sibling.
  [ffe0f7b9c]

* **The upgrade logs everyone out once (schema migration 203)**: fylr's OAuth2
  server is now its own implementation (see *Improved*), and the cutover
  deletes every stored access, refresh, authorization-code and "stay logged
  in" token. Browser users log in again; scripts and integrations fetch a
  fresh token on their next run. The `openid` scope is **no longer accepted**:
  fylr issued `id_token`s nobody consumed, and a request carrying
  `scope=openid` now fails with `invalid_scope` — remove the scope from client
  configurations and scripts that still send it. `read`, `write` and `offline`
  behave as before (only `offline` has an effect: it requests the refresh
  token). [6e1fc2bae]

* **A rejected access token is answered `401` `InvalidToken` on every
  endpoint**: the same dead token used to get three different answers — `400`
  `InvalidToken` from `/api/v1/user/session` and `/oauth2/refresh`, `401`
  `UserRequired` from everything else, `401` `InvalidToken` from a plugin
  callback. A client checking the status alone therefore did not notice on the
  session endpoint or on the refresh, and one checking the code did not notice
  anywhere else. `InvalidToken` existed twice inside fylr and is one error with
  one status now. What a client can rely on: a request that carried **no**
  token is answered `401` `UserRequired`, and a request whose token was
  **rejected** — unknown, expired, revoked, bound to a different browser, or
  belonging to a user who may no longer log in — is answered `401`
  `InvalidToken`, whichever endpoint it was sent to. An integration that tests
  for status `400` together with code `InvalidToken` has to be adjusted, and
  the error's `package` field reads `ferrors` now. Endpoints that serve callers
  without a user, such as deep links and signed asset downloads, are unaffected
  and still answer a request carrying a dead token as they always did.
  [3a962bd35]

* **A file handling configuration saved before this version is migrated on
  update**: EPS and AI rasters are produced from the original now rather than
  from the SVG version (see *Improved*), and whether a file gets that SVG is
  decided beforehand. An instance whose file handling was ever saved carries
  the old wiring in its base configuration — the shipped default is not
  consulted again once that row exists — and the two changes meet badly there:
  the SVG the rasters name as their source is not scheduled for flattened
  artwork, so small, preview and huge were not produced either and such a file
  arrived with no rendition at all. The database migration to schema version
  205 splits the affected entries the way the shipped default declares them:
  WMF keeps the interim SVG, EPS and AI render from the original. The
  configuration form shows the migrated wiring. A configuration that arrives
  with the old wiring after the update — imported from an older instance, or
  posted over the API — is run as it is stored, and the versions left without
  a source fail the way any version with an unreachable source does.
  [630c59a804]

* **`fylr restore --file-api-access-token` is removed; a backup now carries its
  own file authorization.** A restore hands the target the file urls the backup
  stored, and the target fetches the bytes with no session of its own. That
  needed a full source-user access token appended to every url, which put a
  working credential into the request logs of the source and every hop in
  between. It is no longer necessary and the flag is gone — from the CLI, from
  the restore payload and from the migration form in `/inspect`.

  A record's file url is signed instead, for a horizon the backup chooses:
  `fylr backup --file-url-expire-days`, **365 days by default**. The
  `system.file_url_expire.max_days` cap no longer applies to a caller holding
  `system.root`, so nothing on the source has to be reconfigured for a backup
  to be restorable — an automated backup can pull one without involving anyone
  on the other side. Everything else a backup carries a file for — a user picture, a
  pool watermark, custom data on a group or objecttype, a base config value —
  is session gated rather than signed, so the backup packs those bytes and the
  restore uploads them from the backup.

  The horizon is fixed when the backup runs and **cannot be extended
  afterwards**. `fylr restore` checks it before it touches the target and
  refuses a backup whose urls have expired, naming the ways out: take a new
  backup, pack the bytes with `--include-files`, or restore without
  `--file-api` and leave the files behind. [487fd65d74]

* **The easydb plugins are no longer shipped with fylr, and installed ones are
  converted on upgrade.** The distribution used to carry the easydb plugins on
  disk; it does not any more. On upgrade every ENABLED disk plugin that has a
  successor in the marketplace is converted into a url plugin pointing at that
  successor's release, carrying its settings, its granted plugin rights and its
  references from exports, masks and PDF templates. A disk plugin that is
  DISABLED, or has no successor, is not carried over and is removed with the
  rest of the shipped list.

  Two consequences to plan for. **The instance now needs to reach the plugin
  sources** (github.com and programmfabrik.github.io) to download what it has
  been converted to; until a zip arrives the plugin is disabled and shows a
  warning in the plugin manager, where "install as ZIP" can supply it by hand
  from a machine that does have access. And **one plugin is renamed rather than
  kept**: `easydb-editor-field-visibility` becomes `editor-field-visibility`,
  and configuration does not follow a rename, so masks referring to it need a
  manual swap. See the full note under **New**.

### New

* **Base fields only group edits**: `POST /api/v1/db/{objecttype}` accepts
  `base_fields_only=1` to change tags or pools for records editable through
  different masks. Send the group-edit `_id` array without `_mask`; ordinary
  fields, parents, owners and record ACLs remain unchanged. Write permission,
  tag-edit policy and pool permissions still apply. Repeated tag and pool
  edits share unchanged field values between record versions, reducing
  database writes. Bidirectional links are retained and unchanged files do
  not require replacement permission. [4a26c76c3]

* **A video produces preview frames for the player timeline**: videos now get a
  `pages` version — the same `pages.zip` rendition documents already have. It
  holds up to 100 frames of the video, spaced at least half a second apart, at
  200 and 320 px, plus tiled contact sheets carrying all of them. Because
  it is a regular version, rights, signed URLs and `obj_uuid` apply as usual: the
  frame list arrives with `GET /api/v1/eas` in the zip's `info.json`, and a
  single frame or sheet is served straight out of the zip by
  `/api/v1/eas/download/<id>/<hash>/<version>/<path-in-zip>`, range requests
  included. Producing a `pages.zip` is now a format of `fylr convert`
  (`--format pages.zip`) for both documents and videos, and the `fylr pdf2pages`
  subcommand it replaces is gone — a custom recipe that calls it has to be
  changed. A video uploaded from now on produces the version right away, an
  older one when its file is resynced. The version has no settings of its own
  apart from a timeout: the frame sizes, how many frames are taken and the
  layout of the contact sheets are fixed, so the player can rely on finding the
  same thing everywhere. [4eebf3c25, 68a54b280]

* **Plugin marketplace**: fylr now offers a curated, in-app catalog of
  installable plugins. `GET /plugin/marketplace` serves the catalog and
  `GET /plugin/marketplace/{name}/readme` returns a plugin's README on demand
  (both require `system.root` or `system.plugin`). Each entry carries a
  localized short description and a category. Paid and private plugins are
  delivered **sealed** (encrypted), and fylr's built-in keys decrypt them on
  install. A plugin that an enabled plugin depends on cannot be disabled or
  deleted while that dependent is enabled. [f0e99554d]
  The catalog is not compiled into the release: fylr pulls Programmfabrik's
  published catalog sheet at request time and caches it (a stale copy keeps
  serving while a refresh runs), so the offer changes without a fylr update;
  until a first copy could be loaded, the marketplace answers
  `503 PluginMarketplaceUnavailable` and the frontend reports the shop as
  temporarily unavailable. Private release URLs never reach a client: such
  entries are served without their `url` (`installable` marks them), the new
  `POST /plugin/marketplace/{name}/install` installs by catalog name — the
  server resolves the URL and installs missing dependencies first — and the
  manage API withholds the stored URL of an installed catalog-private plugin
  (`url_hidden`; a `null` URL in a save keeps the stored one). [e596ca7d8]
  Catalog entries can carry a `version` and an `updated_at` date, shown on the
  marketplace cards and available for sorting. A plugin's version **is the
  release tag name** of its install artifact — the `version` key in
  `manifest.yml` is retired and no longer parsed or served; for installed
  plugins the release tag is exposed as `build_info.release`. [674c63131]
  Installing a paid plugin from the shop leaves it disabled — enabling one
  needs the license to grant it by name — unless the license already grants
  it, in which case the install enables it right away, so its configuration
  tab is there without enabling it by hand and reloading a second time.
  [487cad950]

* **The easydb disk plugins stop shipping, and are migrated to the
  marketplace**: the images no longer carry `plugin.paths` for them and the
  release archives no longer bundle them. On upgrade each enabled disk plugin
  with a successor becomes a url plugin on that successor's release. Rows are
  matched by manifest name, so an instance keeping its plugins outside the
  image's own directory is migrated too. Eight successors carry a different
  name, and the migration follows that rename into everything keyed by it: the
  plugin's stored settings, the `plugin.<name>.<right>` grants on users and
  groups, an export's producer and transport, and — for the barcode plugin,
  which is a rewrite rather than a rename — the mask splitter type and the PDF
  Creator node, so masks and templates keep working. `commons-library` is
  installed for the custom data types that need it, and `pdf-creator` for
  `fylr-scancode-display`, which requires it where its predecessor did not.
  `server-pdf` is switched off wherever `pdf-creator` is enabled: the two
  declare the same custom events and PDF Creator renders its own PDFs now.
  Configuration carries over except across a rename. [30f15a1c3]
  Starting up no longer waits on the plugin sources. A fylr that cannot reach
  them serves normally within seconds and fetches the zips in the background,
  where it previously did not finish starting at all while the downloads ran
  one after another. Plugin update checks are also spread across the day per
  instance instead of all landing at midnight UTC, and a rate-limited source is
  backed off rather than asked again a second later. [30f15a1c3]

* **License-gated plugins**: A signed license can list which plugins an
  instance is allowed to enable, through a `plugins` capability map. A plugin
  the license names without granting it (`"enabled": true`) is force-disabled
  at runtime — the stored `enabled` flag is kept, so the plugin re-enables by
  itself once the license grants it again — and enabling it over the API is
  refused with `PluginNotLicensed` (403). Plugins the license does not name at
  all stay unrestricted. The plugin-manage API now reports each named plugin's
  license capability block (an empty `{}` when it grants nothing) and omits the
  field for unnamed plugins. A not-licensed plugin is inactive, so — like an
  admin-disabled one — its section is left out of the base config; any
  configuration it had stored is preserved and returns once the license grants
  it again. See
  [License management](https://docs.fylr.io/license-management). [d879cae2f] [297a219921]
  Which plugins are paid is the marketplace catalog's word, matched by plugin
  name for every install path (URL, ZIP upload, mirror) and applied in both
  directions: freeing a plugin in the catalog frees existing installs too
  (re-checked periodically), while a catalog without an entry for the name
  never silently changes the flag. [1088324b2]

* **Plugin callbacks can write into the saving transaction**: A server-side
  plugin callback (`db_pre_save`, `transition_db_pre_save`, collection upload)
  now receives an `api_tx_url` alongside its access tokens. `/db` requests
  sent to that URL run **inside the request's open write transaction**, so
  objects the plugin inserts or updates commit — or roll back — atomically
  with the save that triggered the callback, and are readable back within the
  same transaction. The callback's `plugin_user` identity works there too. The
  URL is bound to the single request and still requires the callback's bearer
  token. A failed write on that URL fails the save as a whole: the transaction
  is refused at commit and nothing — neither the save nor the plugin's earlier
  writes — becomes durable, so a plugin cannot leave partial state behind by
  ignoring an error. `await_index` is not available on this URL (the index
  jobs only become visible once the saving request commits). Behind NAT or a
  load balancer the URL's host honors `callbackBackendOwnURL`, like the
  execserver pipe URLs. See the
  [plugin callback documentation](https://docs.fylr.io/for-developers/plugin/callbacks).
  [2011b1984]

* **3D assets**: files with the extensions `splat`, `spz`, `ksplat`, `ply`,
  `ply.zip`, `ply.gz`, `stl`, `obj`, `3ds`, `glb`, `gltf`, `nxs` and `nxz` get
  the new file class `3d`. fylr renders the preview images itself — a new CPU
  rasterizer in `fylr convert` draws the scene and picks the best viewpoint
  automatically — for everything it can decode: gaussian splatting scenes
  (`splat`, `spz`, and `ply`, also zipped or gzipped, binary and ascii) and
  polygon meshes (`ply` carrying faces, `stl`, `obj`). A `.ply` is both
  formats and only its content decides which. Those sources additionally get
  a compact `splat` interchange rendition for the webfrontend's 3D viewer,
  carrying gaussians or triangles as the original turned out to be. The
  remaining extensions are accepted and classified, but not decoded. The
  rendering camera can be stored per asset (like the custom video thumbnail)
  through the `splat-view-select` produce parameter; `fylr convert
  --splat-view` accepts COLMAP/3DGS camera matrices. [7d5129cf2]

* The produce config a class exposes over the API (`GET /api/v1/settings`)
  now states the extensions the class accepts on upload, not only those it
  produces versions for, so the base configuration editor can offer the
  accepted-but-not-decoded formats as well.

* **Download dialog options are grantable per user and group**: a new
  `frontend_features` parameter, **Download Options**, controls which optional
  sections of the download dialog a user sees — `filename` (the file name
  section), `variants` (the "include file variants" option) and `custom` (the
  custom rendition / on-demand version section) — each grantable on its own.
  Like the other `frontend_features` flags it is advisory to the frontend;
  nothing on the server is gated by it. Existing installations are unchanged:
  the upgrade turns all three choices on for every user and group that already
  holds the download right, so the dialog looks exactly as before until an
  administrator removes a choice. [52d48fd52]

* **360° media are recognized**: a spherical video or a panoramic image now
  carries the technical-metadata key `projection_type` (for example
  `equirectangular`), so an application can tell a 360° asset from a flat one.
  fylr reads the Spherical Video metadata — the V1 XML block, and the V2
  `sv3d` box and Matroska `Projection` element via ffprobe — as well as the
  XMP GPano tags of images. Produced versions keep the marker: the production
  re-adds the Spherical Video V1 box to MP4 renditions and the XMP GPano tags
  to image renditions (even with `strip`), as long as the conversion keeps the
  full equirectangular frame (no crop, rotate or mirror). See
  [File worker](https://docs.fylr.io/for-developers/file-worker).
  [6ea606aef] [44120f79b]

* **Produce new versions from videos**: `POST /eas/produce` now accepts video
  originals, not only images. A video parent can be trimmed (`trim.start` /
  `trim.end`, seconds on the source timeline), muted, rotated in steps of 90°,
  mirrored, cropped, scaled to a target `height`, and color corrected through
  the new `color` object with the classic grading controls — temperature,
  tint, exposure, contrast, highlights, shadows, whites, blacks, saturation,
  vibrance and hue, each neutral at `0`. Target formats are `mp4`, `mov` and
  `m4v`. As for images the production runs asynchronously: the response
  returns the new file `pending`, poll it until it is `done` or `failed`
  (an unsupported rotation or an out-of-range color value fails there, not on
  the request). Image parents are unchanged, except that `webp` sources are
  producible now — the recipe's extension list is the single gate, replacing a
  duplicated list in the system produce config that had drifted from it. See
  [POST /eas/produce](https://docs.fylr.io/for-developers/api/endpoints/eas/produce).
  [f4be96604]

* **Plugin manager shows a README tab for installed plugins**: a plugin's
  docs are the `README.md` it ships next to its `manifest.yml` — the same
  file the marketplace "more information" already reads. Reading the plugin
  content (install/update/load) stamps `manifest.has_readme` into the manage
  listing, and the new `GET /plugin/manage/{id}/readme` serves the content on
  demand, memoised per content version for url/zip plugins. The retired
  `plugin.webfrontend.readme` manifest key is rejected by fylr-build-plugin
  v1.4.0; geo-json v1.3.6 and obscure-image v0.5.12 already ship their
  README next to the manifest. (419d82c60)

* **Plugins report an unreachable source instead of failing silently**: when
  fylr cannot fetch a `url` plugin's source, the plugin manager now shows a
  warning triangle in front of the plugin name with the reason and since
  when — the stored `warning` (`url_unreachable`, `url_http_error`,
  `zip_invalid`) is served by the manage API and cleared by the next
  successful fetch. A plugin whose ZIP is already stored keeps running on the
  last downloaded version (updates resume when the source returns); a plugin
  whose ZIP never arrived (`state: "not_installed"`, e.g. after the disk→url
  migration) is force-disabled at runtime like an unlicensed plugin — the
  stored `enabled` flag keeps the user's intent, so it starts by itself once
  the download succeeds. **Erneut versuchen** in the plugin manager forces a
  source check right away (`POST /plugin/manage/{id}/check`) instead of
  waiting for the update policy's window, and **Als ZIP installieren** rescues
  a plugin whose source the server cannot reach: the browser fetches the ZIP
  and uploads it onto the same plugin, which becomes a `zip` plugin keeping
  its name, configuration and enabled state. A settings-only save no longer
  contacts the source at all, so a plugin with a broken source can still be
  reconfigured or disabled. Upgrade runs schema migration 202. (2e14701dd)

* **The plugin marketplace can be switched off**: `plugin.marketplace.enabled:
  false` removes the shop from the plugin manager, and fylr then never fetches
  a catalog or source URL — for air-gapped installations, or where plugins are
  chosen centrally. The marketplace endpoints answer
  `400 PluginMarketplaceDisabled`. (2e14701dd)

* **One bounded HTTP client for fylr's outbound requests**: plugin sources,
  webhooks, execserver callbacks, e-mail images, backups and exports now share
  a client that bounds connect, TLS handshake and the wait for response
  headers — a remote that accepts the connection and then stalls used to hang
  the request forever, and a single dark plugin source froze plugin updates
  instance-wide. Plugin probe and download are additionally bounded per
  operation, which the transport timeouts cannot cover. The timeouts, the
  HTTP/2 switch and per-URL overrides all live under `fylr.debug.http`;
  `fylr.debug.disableHttp2Client` keeps working.
  (2e14701dd)

* **`/inspect/system/topology` shows the whole installation at once**: every
  fylr server, every execserver, the load balancer when there is one, and the
  work moving between them — what is running, what is queued behind a full
  waitgroup, what finished and what failed, with throughput and bytes moved.
  It updates over a websocket rather than by polling, and the same data is
  available as JSON at `/inspect/system/topology/data`. An execserver now
  registers what it knows about each fylr connected to it (backend id, name,
  version, callback URL), and verifies at connect time that the announced
  callback URL really comes back to that server — so a callback address
  pointing at a load balancer in front of several replicas is reported on the
  page instead of failing later inside a job. An address fronting a fleet is
  recognised from the connection itself, so a Kubernetes Service with a single
  pod behind it is still shown as a Service. [ffe0f7b9c]

* **A config key fylr does not know is reported instead of ignored**: until now
  a key that the configuration no longer has — a typo, or a setting renamed by
  an upgrade — was dropped without a word when the config was read, so whatever
  it was meant to configure silently had no effect. Every config file is now
  checked against the settings fylr knows: unknown keys and keys that still
  work but are deprecated are logged as warnings at startup (the server starts
  regardless), listed on the `/inspect` config page with the file each one
  stands in, and reported by the new `fylr config check <file>...`, which reads
  the configuration the same way the server does without starting anything and
  exits non-zero when a key is unknown or the config does not load — for
  validating a config before a restart, or in a CI that renders one. `--strict`
  makes it fail on deprecated keys as well. Mistyped `-s` parameters, which
  used to be ignored just as quietly, are reported too; the environment is not
  checked this way, since a container carries `FYLR_` prefixed variables that
  are not meant to be configuration. The first run of the check found that
  `fylr.example.yml` itself could not be loaded (a duplicate `marketplace` key)
  and documented a plugin default under a key that does not exist; the shipped
  example is corrected and a test keeps every config file in the repository
  free of unknown keys. [4d90c3915]

* **Technical metadata says whether an image carries transparency**:
  `technical_metadata.alpha` is present, and true, only for a file or rendition
  that has an alpha channel. Nothing else in the technical metadata answered
  that question — the channel count is a TIFF tag and the colour space names
  only the colour channels — so whether a conversion kept a logo's transparent
  ground or put it on a white plate could not be told apart from the record.
  [2ea62b3006]

* **`/inspect/datamodel/<id>/model/` draws the object types of a datamodel and
  what links them**: the net on the left, and picking an object type fills a
  panel on the right with its columns, its masks and their fields — without
  leaving the picture. One line per relationship, with the arrowhead at the
  object type that holds the column, and an `R` where the relationship reads
  from either end (a reverse link, a hierarchy, or a bidirectional column; the
  line's tooltip says which). A master and the object types it owns are drawn
  as one box rather than as arrows, and every object type also keeps a node of
  its own. Chips carry the facts the table cannot show at a glance — main
  search, pools, tags, hierarchy — and how many objects each object type
  actually holds, so a model as designed can be told from a model as used. The
  object types can be filtered to the main search or away from it, the
  unlinked ones hidden, and on a model with hundreds of links the lines
  switched off entirely. Linked from the datamodel page, and available as JSON
  for either half. [e95288943]

* **execserver, temporary CPU allocations**: a command running under an
  auto-balancing execserver can ask for more CPUs from the shared pool while it
  runs a parallel subprocess, through a loopback callback the execserver passes
  in `FYLR_EXEC_CONTROL_URL`. `fylr convert` does this around FFmpeg: the video
  encode asks for up to `FYLR_CONVERT_VIDEO_MP4_THREADS` CPUs (unset: whatever
  the pool can spare), a single frame for two, AAC and MP3 for one, and the
  extras go back to the pool when FFmpeg ends. They never take the
  `fastReserve` slots, so short interactive work still finds a slot during a
  long encode, and the new `fylr.services.execserver.maxCpusPerJob` caps what
  one command may hold in total (0 = cpus minus the reserve); a `-threads` in
  the ffmpeg command arguments of the execserver config caps the request as
  well. Every execserver command now carries `FYLR_EXEC_SUPERVISED=1`, and the
  helper programs `fylr convert` and `fylr metadata` start stay in the
  command's process group on every install: the memory and stall watchdogs see
  them, which also means a converter step now counts toward the per-job memory
  ceiling. The broker status and the `/inspect` topology show held extras as
  `extra_cpus`, and the gauge `fylr_execserver_extra_cpus` carries the same
  number. [bebc44b55]

### Improved

* **Colorspace of a custom version**: A colorspace an ICC profile can express
  is converted through that profile and the produced file carries it —
  `rgb`/`srgb` through `sRGB_IEC61966-2-1_black_scaled`, `gray`/`grey` through
  `Generic Gray Profile`, `cmyk` through `ISOcoated_v2_eci`. Previously the
  conversion was ImageMagick's own channel arithmetic and the file came out
  untagged, which for CMYK is not what a print shop expects. A colorspace no
  profile expresses (`YCbCr`, `HSL`, …) is converted as before. Set together
  with a colour profile the two have to agree: a `cmyk` colorspace with an RGB
  profile is refused when the preset is saved, where before one of the two was
  silently dropped. [920577b09]

* **Zoom of a transparent image**: A transparent PNG keeps its transparency in
  the zoom. Tiles requested as PNG are transparent; tiles requested as JPEG,
  which has no alpha channel, are laid on white as they always were.
  [920577b09]

* **Janitor**: Download retention is now configurable (default: one day),
  and unscheduled exports can expire after a configurable period without a run.
  Rerunning renews that period, including empty or failed runs. Historic file
  cleanup runs before export expiration and unused-file deletion, allowing
  previously downloaded files to be reclaimed when no references remain.
  [c4eba7428]

* **Janitor**: Two new tasks remove what a purge or a re-saved record leaves
  behind. `terms_delete` drops terms no record links to anymore and removes
  them from the suggest index; `custom_data_delete` drops custom data entries
  no value refers to anymore, so the custom data type updater stops refreshing
  dead entries. Both wait an hour after a row's creation and list their next
  batch on `/inspect/system/janitor/`, where they can be run by hand. A manual
  janitor run may carry `run_time`, and every age gate of that run then treats
  the given instant as now. The upgrade adds a creation time to the term table
  (schema 209); existing terms count as old, so the first sweeps after the
  upgrade clear the backlog in batches. [55c269e16]

* **Object loading**: Linked and historical reads reuse owner and group
  lookups within a request, and cached reads fetch only the required standard
  entries. Standard construction and reading date fields use fewer temporary
  allocations, reducing memory and garbage-collection work when rendering
  batches. [4a26c76c3] [5d8a11644]

* **The event stream takes its access token from the websocket handshake
  header**: `GET /api/v1/event/stream` accepts the token as an entry in the
  `Sec-WebSocket-Protocol` header — `fylr.auth.bearer.<token>`, the token
  base64url-encoded without padding, offered alongside the real subprotocol
  `fylr.event.v1`, which the server echoes back. A browser cannot set request
  headers on a websocket handshake, so this is the only way a web client can
  authenticate without putting the token into the url, where it would end up
  in server, proxy and browser logs. The token is read only from an actual
  handshake, and only before the upgrade: an unauthenticated handshake is
  still refused with 401 and no connection is opened for it. The
  `access_token` query parameter keeps working unchanged, so existing API
  clients need no adjustment. A handshake the server refuses now answers with
  the usual JSON error (`WebsocketUpgradeFailed`) instead of a plain-text
  response. [add7bde1f]

* **A plugin ZIP installs regardless of the file production settings**: the
  plugin manager uploaded a plugin's ZIP like any other asset, so the file
  production settings governed it — an instance that does not allow unknown
  file types refused the upload with `Filetype "zip" is unknown and not
  allowed`, and a configured maximum upload size refused ZIPs above it. A
  plugin ZIP is an internal artifact, not user media, and is now exempt from
  both. It also no longer travels as an uploaded asset: `PUT
  /plugin/manage/upload` takes the ZIP as the raw request body and installs
  the plugin, `POST /plugin/manage/{id}/upload` replaces the ZIP of an
  installed plugin, and `GET /plugin/manage/{id}/zip` returns the stored ZIP.
  Plugins of any size can be installed, an artifact that is not a plugin ZIP
  is refused and not stored, and `zip_file` is no longer part of the plugin
  management API. A plugin's `type` now follows its content: uploading a ZIP
  onto a `url` plugin turns it into a `zip` plugin — that is what **Als ZIP
  installieren** does — while a JSON save carries no content and no longer
  changes the type at all. [4c58c62fb, 6250def51]

* **Frontend staging hosts at `*.web.fylr.io` are trusted webOnly origins**:
  the baked-in `loginAllowRedirects` default now includes
  `https://*.web.fylr.io` (the successor of `*.web.fylr.dev`), so per-branch
  frontends served there can log into a fylr
  via the cross-server feature without per-instance configuration. Configs
  that set their own `loginAllowRedirects` list are unaffected.
  [024304e14]

* **Execserver scheduling and execution limits**: fylr grants a
  job to a free execserver slot the moment one opens, instead of the execserver
  polling for work. Without an explicit `waitgroups` block the execserver runs
  a single CPU pool and classifies each service light or heavy by its measured
  runtime, reserving a few slots (`fastReserve`) so short interactive jobs
  (plugins, metadata) keep running promptly while long conversions are busy;
  the learned per-service profile survives restarts. A fylr behind a single
  load-balanced execserver address (for example a Kubernetes Service in front
  of several pods) now spreads work across the whole fleet on demand, opening
  more pooled connections when jobs back up — no per-pod addressing or headless
  Service required, so `tokenResponseSendServerIP` is no longer needed
  (`callbackBackendOwnURL` is the optional override for NAT topologies). On
  shutdown an execserver drains: it finishes running jobs within
  `execserver.drainTimeoutSec` (default 20s) and answers any interrupted
  request with a retryable "stopped for maintenance" receipt (`503
  ExecStopped`) that clients retry automatically. The new tuning keys `cpus`,
  `fastReserve`, `heavyThreshold`, `unknownShare` and `drainTimeoutSec` are
  documented in `fylr.example.yml`. [dc23ded29]

  Jobs now run within an automatic memory budget derived from host RAM or
  the lower Linux container limit. Auto-balancing uses learned service
  footprints when admitting jobs, and memory supervision aborts commands
  that exceed their individual ceiling or the shared budget. Inspection
  shows the budgets, footprints and sampled peak memory. Sampling runs once
  per second; operating-system memory limits remain necessary to enforce a
  strict bound between checks.

  Commands that make no progress for ten minutes are stopped. CPU activity,
  transferred bytes, output and growing work files count as progress. Set
  `fylr.services.execserver.stallTimeoutSec` to change the default, or use a
  recipe's `stallTimeout` duration; `"0"` disables stall supervision. Recipe
  `timeout` durations remain wall-clock ceilings, including explicit `"0"`
  for unlimited execution, and invalid durations are rejected. Long video
  encodes now have a 12-hour ceiling. Receipts distinguish timeouts, stalls
  and memory aborts; active job directories are protected from janitor
  cleanup. [c7cc099cd]

* **API responses no longer send the `X-Easydb-Base-Schema-Version` and
  `X-Easydb-User-Schema-Version` headers**: these easydb5-era headers exposed
  internal schema versions with every response and had no remaining consumer.
  Clients tracking cache invalidation should use `X-Fylr-Cache-ID`, which is
  still sent. [0fe459288]

* **CORS: credentialed cross-origin requests are limited to the origins the
  configuration already names**: an `Origin` is reflected together with
  `Access-Control-Allow-Credentials: true` when it is the `fylr.externalURL`
  origin, matches a `fylr.services.webapp.loginAllowRedirects` pattern
  (cross-server webOnly frontends) or is the origin of a redirect URI of a
  registered OAuth2 client — so the web frontend keeps working in split and
  cross-server deployments, and no new configuration is introduced. Every
  other origin receives the credential-less `Access-Control-Allow-Origin: *`
  and authenticates with a bearer token, as before. A response to a request
  that carries no `Origin` header carries no CORS headers — only browsers
  evaluate them — and every response now carries `Vary: Origin`. The
  `Access-Control-Allow-Private-Network` header is no longer sent.
  [0fe459288] [ad272dc93]

* **Security policy headers on every response**: fylr now sends
  `Referrer-Policy: strict-origin-when-cross-origin` — the full URL (file
  signatures, OAuth codes, one-time page tokens) never leaves the origin,
  cross-origin only the bare origin is sent, which keeps Referer-keyed
  map/tile services working — `X-Content-Type-Options: nosniff`, so a browser
  trusts the `Content-Type` fylr declares instead of guessing one from the
  body, which matters most for the file endpoints that deliver uploaded bytes
  inline from fylr's own origin — and, by default, `X-Frame-Options: SAMEORIGIN`
  plus the equivalent `Content-Security-Policy: frame-ancestors 'self'`
  (fylr's own login frames itself, so same-origin framing stays allowed). A
  portal that embeds fylr in a cross-origin iframe is admitted via the new
  `fylr.services.webapp.frameAncestors` list, documented in
  `fylr.example.yml`: its entries extend `frame-ancestors`, and
  `X-Frame-Options` is then omitted since it cannot express an allow-list.
  Browsers validate the whole ancestor chain, so the portal origin must be
  listed even though fylr's internal iframes are same-origin. [e9e8a7c6d]
  [00d56743c]

* **SQLite backend hardening**: plugin callbacks, uploads and background work
  now behave under SQLite's single-writer lock. Callback tokens are minted
  before the saving transaction opens, write-lock contention surfaces as a
  retryable `423 DatabaseLockError` instead of an opaque failure, background
  workers back off instead of stampeding the lock, and a number of
  SQLite-dialect errors (unique constraints, expression indexes) are now
  reported as their proper API errors. Background writes are additionally
  bounded: the per-user `last_seen_at` touch runs at most once per user at a
  time, failed event flushes retry paced instead of per incoming event, and a
  worker's error back-off is served in full instead of being bypassed by
  wakeup signals. Deleting a mapping that a pool uses as its dc-export /
  image-export / image-import mapping detaches it on SQLite too — existing
  databases are migrated (schema 200) — and an `elastic.parallel` override
  from the environment or command line now reliably wins over the SQLite
  default clamp. The case-insensitive collection filter on
  `/inspect/collections` folds full Unicode on SQLite. CI exercises the
  critical API surface against a SQLite instance on every build.
  [2011b1984] [bdd48a4160]

* **Collection load errors are logged with their real cause**: Loading a

  additionally logged with its full cause. [5f59ffe54]

* **Audio conversion: selectable format and bitrate, localized recipe texts,

* **Plugin sealing via fylr-build-plugin**: sealed (encrypted) plugins are

* **Installing a url plugin no longer sends its ZIP through the file metadata

  sleeps a fixed second before it first checks whether the ZIP has landed.

* **Deep links into ZIP files name their one restriction**: requesting a path

  read into a ZIP. [35e6bb46f]

* **API documentation: error responses grounded in real error codes**: every

* **File worker base config order**: in the base configuration's File Worker

* **A metadata mapping that writes nothing is logged as a warning**: when a
  mapping produced no value for any writable field, the background task noted
  it at info level, which is easy to miss in a long run. Such a skipped object
  is logged as a warning now, at the same level as the neighbouring "no
  mapping found" and "mapping not supported for this file" messages.
  [0d96a8076]

* **Dates are searchable in the full text**: a date, datetime or daterange
  field with the mask's full-text option enabled contributes its searchable
  strings to the record's full text — the ISO form, the value as it is
  rendered in each database language, and the year. A date range additionally
  matches every year it covers, and its textual representation (which replaces
  the rendered dates for display) is searched word by word. B.C. dates are
  found by their localized rendering ("1000 v. Chr.") and by the displayed
  year, never by the raw ISO year (`-0999`). Until now the option had no
  effect on date fields at all, so such a value was only findable through the
  standard-field rendering. The autocomplete stays narrower than the full-text
  search on purpose: it offers only what a record actually displays — the
  localized renderings, or the entered text of a range — while the ISO forms
  and the years a range spans remain full-text-only. [6585e4023]

* **Masks below the line in a pool are no longer indexed**: a record was
  written to the search index once per mask of its objecttype, whatever the
  pool allowed — the standard masks of a pool only filtered the search, so the
  documents of a deactivated mask stayed in the index and merely stopped being
  returned. That is what easydb 5 documents for pool and objecttype
  ("if `_standard_masks` contains a subset of all masks, only these will be
  indexed"), and what an instance with several masks per objecttype notices as
  a needlessly large index. A record is now indexed only under the standard
  masks of its pool — inherited from the parent pools, falling back to the
  objecttype and finally to all of its masks, so an instance that configures no
  standard masks anywhere is unaffected. A mask right that names an excluded
  mask does not bring it back: the pool decides whether the record is findable
  under that mask at all. Because both the standard masks and the mask filters
  are evaluated while indexing, `POST /pool` and `POST /objecttype` now answer
  a change with a 202 that names how many records it re-indexes and carries a
  `confirmReindex=yes` button; confirmed, those records are queued into the
  running index at low priority — for a pool including its sub-pools — so the
  documents are added and removed in place, without building a new index and
  without blocking the frontend. Reordering the masks changes nothing: the
  order picks the best mask per search request and is not stored in the index.
  [f33fe8206]

* **The /inspect object list sorts by version count**: the object list of an
  objecttype (`/inspect/objects/<objecttype>/`) offers "Version ↑/↓" in its
  **Order** select, which sorts by how many versions a record has — the view
  that shows at a glance whether records collect versions unexpectedly. The
  order comes from the version number of a record's latest row, which is its
  number of versions, so no count over the historic rows is involved; sorting a
  large objecttype this way reads all its rows, so expect the page to take a
  moment. The list itself now opens with the **newest records first**
  (`system_object_id DESC`), where it used to open with the oldest.
  [3b8a30713]

* **A recipe setting the production cannot use is refused when the config is
  saved**: the file production settings checked a version for structure — its
  name, its extensions, that the recipe exists and fits the class — but not the
  values handed to the recipe. A size outside the range the recipe allows, or a
  format it does not offer, was saved without a word and then failed on every
  file of that class, visible only as a sync error per file (`Value '200' is
  lower than minimum allowed '201' in 'min_size'`). Saving now fails right away,
  naming the setting and the limit it violates, for the versions as well as for
  the custom metadata entries. A configuration stored earlier still loads, so an
  instance whose settings fell out of range through an update keeps running and
  reports it on the next save. [68a54b280]

* **The backup and restore tools log through fylr's own logger**: the last
  logrus usages are gone, so every fylr command writes through the configured
  logger. `backup.log` and `restore.log` keep their format and their file
  handling, but their debug lines now follow `--verbose` like the rest of the
  output, so a run without it writes fewer lines than before. On the server, a
  handful of messages from the rights, object and transition code that used to
  go to standard error in a format of their own now honour `fylr.logger`: they
  follow its format and its level and appear in the same log everything else
  does. [2727b223a]

* **A user record names the groups the user is automatically in**: the
  groups a user belongs to by virtue of their type — `Alle Benutzer`,
  `Lokale Benutzer`, `LDAP-Benutzer` and the rest — follow from a rule
  rather than from a stored membership, and `GET /api/v1/user/<id>` left
  them out. Reading another user therefore never showed which system
  groups apply to them, and the user manager had the same blind spot.
  `_groups` now carries them, marked `_automatic_auth` with the type
  `implicit`, so an implicit membership stays distinguishable both from
  one an administrator assigned and from one a group rule confers
  (`system`).
  It is the same list `GET /api/v1/user/session` returns as `groups`,
  which gains the same marker, and the response to a `POST /api/v1/user`
  now matches a `GET` of the user right after instead of omitting the
  rule-based memberships. Backups and the search index are unchanged:
  there is nothing stored behind these entries, and a restore drops them
  again. In the user manager they appear under **Automatische Gruppen**,
  where they cannot be edited. [0f73ad852]

* **What a metadata mapping actually ran is recoverable**: a produce or
  metadata run stores the job receipt of its execserver call in the event it
  writes, and that receipt is the only record of the command that was
  executed. It was reachable only inside the raw `info` dump, where the
  interesting part sits several levels down in an escaped JSON string — a
  plugin passes its whole payload as one `--info` argument, so the prompt an
  AI recipe sent sits behind a configuration blob of a few dozen kilobytes.
  `/inspect/events/<id>/` now has a **Run** section with the shell-quoted
  command line, a copy button, the arguments one per row, and stdout and
  stderr; a JSON argument renders as a tree. A background task names the
  events of the recipe runs behind its values, as `event #<id>` that
  `/inspect/tasks/<id>/` links, and reports what those runs had to say: a
  recipe's mapping configuration can declare `json_warnings` next to
  `json_error`, a gjson path to a list of strings in the metadata it
  produced. Unlike an error a warning does not fail the mapping — the values
  apply and the task writes one **WARNING** line per warning, naming the
  recipe. [8a933ae31]

* **A rendition produced the same way for several formats is one entry**: the
  default produce configuration described each class as extension groups cut
  by what a format gets *in addition* to the shared previews — the splat
  interchange version for 3D, the AAC version for audio, the SVG for EPS and
  WMF — and wrote out every version of every group. The shared previews are
  identical across those groups, so **Datei Erzeugung** listed one rendition
  two, three or four times over. The 3D class was the visible case: two blocks
  of *250px*, *1000px* and *1000px (Wasserzeichen)*, same source and same
  recipe, differing only in which extensions each row carried — and editing one
  of the copies changed the rendition for some of its formats and not the
  others. A version that comes out identically for several extension groups is
  now a single row covering all of them: 3D goes from seven rows to four, audio
  from eight to four, office from fifteen to eleven and images from 21 to 19.
  The rows that stay doubled differ for real, such as the JPEG and the PNG
  preview of the image class. Nothing about what is produced changes — this is
  the same configuration written once instead of several times — and an
  instance with its own produce configuration keeps what it has until it resets
  a class to the default. [e7a2f4bc1]

* **fylr's own OAuth2 authorization server replaces the fosite library**: the
  wire format is unchanged — token prefixes, endpoints, RFC 6749 error
  responses — as are the four grants fylr serves (authorization code with PKCE
  `S256`, password, client_credentials, refresh_token), multiple redirect URIs
  per client, session browser-binding, "stay logged in" and SAML logout. The
  OpenID-Connect provider surface is gone rather than reimplemented: no
  `id_token` is minted, and `.well-known/openid-configuration` stays as plain
  OAuth2 endpoint discovery without the id-token signing metadata. The web
  frontend now requests its scopes (`read write offline`) explicitly.
  [6e1fc2bae]

* **Saving into a hierarchical objecttype no longer slows down as it fills
  up**: to give a new top-level object its child index, fylr asked for the
  highest one already in use with a `MAX()` over every object of the
  objecttype, once per save. An aggregate over that join cannot stop early, and
  while an instance is being filled — a bulk import, a restore, an instance
  that was just purged — the database has no statistics for the tables yet and
  plans it as a nested loop, so the cost grew with the square of the
  objecttype: inserting 1000 objects took 269 ms into an empty objecttype and
  3579 ms once 10000 were in it, for exactly the same work. The query reads the
  single top row from an index now (`value_idx_15`, schema 204) and the time
  stays flat, 263 ms for the first thousand and 530 ms for the last. Only
  objecttypes with a hierarchy were affected. The same schema step drops
  `value_idx_4`, whose only user was the old query. [d40f2c216]

* **EPS and AI files render with ghostscript, and only get a vector rendition
  when one is usable**: previously every version of a PostScript-family file
  came out of an interim SVG produced by inkscape, which holds such a document
  as an editable DOM at roughly 32 KB per element. Illustrator's transparency
  flattener routinely turns one artboard into a few hundred thousand elements,
  and one 5 MB EPS measured 6.7 GB of memory in inkscape against 68 MB in
  ghostscript for the same picture. The rasters now render from the original
  with ghostscript — or, cheaper still, from the file's embedded preview when
  it carries one large enough for the requested version — and the SVG version
  is a rendition of its own rather than the source of the others. Whether a
  file gets that SVG at all is decided before the version is scheduled, from
  the new `technical_metadata.vector` counts of embedded images and shadings:
  flattened artwork would convert to a faithful quarter-million-element SVG
  that no browser opens, so for such a file the version is not produced, and
  does not appear as a failed one either. A custom produce config can gate on
  the same counts — a nested `technical_metadata` member is now available as a
  recipe replacer, e.g. `%_source.technical_metadata.vector.images%`. WMF is
  unaffected and still goes through inkscape, which is the only tool that
  reads it. Files already in the system keep the versions they have until
  their file is resynced. [62205dcf7]

  The SVG version is written by `mutool` rather than by `pdftocairo`: a PDF
  blend mode has no browser-renderable form in the latter's output, so the
  vector rendition of an Illustrator file that used one drew nothing at all in
  Chromium. It is also the smaller and faster converter, and closer to the
  rendered picture on half the files measured. An .ai is measured and framed
  by the page ghostscript actually renders, which for such a file is its PDF
  page rather than the PostScript header's bounding box — the two disagree,
  and on one file the record called it portrait while every version of it was
  landscape. An embedded preview only serves a version when it shows the page
  in the shape the page has, so Illustrator's square thumbnail no longer
  decides the aspect of `small` on its own. [2ea62b3006]

* **Illustrator files older than version 9 convert at all**: such a file is
  PostScript written in Illustrator's own abbreviated operators, whose
  definitions the application or the printer supplied — the file itself
  carries none, so every renderer in the toolchain stopped on its first token
  and an archive of that vintage arrived as assets whose every version had
  failed. fylr now supplies the missing operator definitions to ghostscript
  and renders the file, as a second attempt after the normal one failed and
  only for a file that carries the old `Adobe Illustrator(TM)` creator line
  with no procset of its own — a self-contained file keeps the operators it
  defines for itself, and a successful retry leaves no error behind in the
  receipt. A file that still fails now names the operator ghostscript stopped
  on instead of reporting a generic conversion failure. [62205dcf7]

* **System purge returns about a second sooner**: every purge paid a fixed
  one-second worker-shutdown grace and ran the database purge script twice.
  The workers now signal completion — the second stays only as a cap — and
  the script runs once. Across the CI suite's ~900 purges this alone
  recovers about 15 minutes of compute. [baa7e4273]

* **Apitests wait less and the apitest tool decodes on json/v2**: the shared
  `_setup` index waits poll on a 200/250 ms grid instead of 0.5–1 s
  [ade2c7f20], and the apitest tool decodes generic JSON on the Go 1.27
  `encoding/json/v2` engine, a third less client CPU with byte-identical
  semantics [6120559a28]. Same-host CI legs run ~11% faster.

* **Dependency refresh**: all direct Go dependencies move to their latest
  versions. `github.com/go-ldap/ldap` moves to the current v3 module, YAML
  handling converges on `go.yaml.in/yaml/v4`, and UUIDs come from the Go
  standard library instead of `github.com/gofrs/uuid`. [d671692707] Two
  libraries fylr does not use directly but reaches through the cloud storage
  client follow: `google.golang.org/grpc` and `go.opentelemetry.io/otel` move
  to versions that close vulnerabilities listed in the Go vulnerability
  database. [70c43c8c9d] The build now checks that database on every run, so a
  dependency that becomes known-vulnerable is reported rather than waiting for
  someone to look. [93a8b881ba]

* **A round of plugin updates refreshes the API cache once, not once per
  plugin**: every plugin whose ZIP the plugin updater fetched or replaced
  invalidated the API cache on its own, and each invalidation makes the server
  rebuild that cache whole — configuration, plugins, events, data model, object
  types, pools, tags, workflows and rights. Where many plugins are fetched in
  one round, which is what a start looks like when plugins were just installed
  from URLs or when the instance was offline while its plugin sources were
  unreachable, that cost one full rebuild per plugin, and repeated the same
  plugin warnings in the log once per rebuild. A round now invalidates the
  cache once, when it has finished: seventeen plugins fetched at startup cost
  one rebuild instead of eighteen. A change outside such a round — installing a
  plugin, the plugin manager's forced source check — is published immediately,
  unchanged. [07f96da2fc]

### Fixed

* **Inspect janitor page**: The exports section folds under a "Next batch"
  heading like every other section instead of standing open. [55c269e16]

* **BMP downloads**: A custom version downloaded as BMP arrived as a 32 bpp
  file whenever the source carried an alpha channel, a shape many BMP
  consumers cannot read. A BMP is written as 24 bpp TrueColor again, as it was
  before the convert step began using vips. Reading a BMP is unaffected.
  [920577b09]

* **Colour profiles offered for a download**: `Generic XYZ Profile` and
  `Generic Lab Profile` are no longer among the built-in profiles. XYZ and Lab
  describe the space colour management converts *through*, not image data, so
  a file tagged with one is refused by colour-managed software although the
  image inside it is intact — a download could not be opened for that reason
  alone. **A custom version preset naming either profile no longer saves** and
  has to be changed to a real profile, for example `sRGB Profile` or
  `AdobeRGB1998`. [920577b09]

* **Zoom of a BMP, and the transparency of one**: the zoom renders BMPs of
  either colour depth instead of failing on 32 bpp, and a BMP that declares an
  alpha channel is reported with `alpha` in its technical metadata, as PNG and
  TIFF already were. [920577b09]

* **Topology page and secured OpenSearch**: the health probe on
  `/inspect/system/topology` now authenticates with the configured elastic
  credentials. A cluster with the security plugin answered the anonymous
  probe with a plain-text 401, shown as `invalid character 'U' looking for
  beginning of value`; a refused probe now reads `HTTP 401 Unauthorized`.
  The execserver's balance-seed restore line names the pod that wrote a
  shared seed instead of reporting a hostname change. [2721429cb]

* **Bidirectional links**: Confirming unlink while deleting a record now
  removes both directions before the record enters the trash. Restoring it
  keeps those links removed. The same behavior applies to background deletion
  tasks. [ee947c7b6]

* **Recursive standards and indexing**: Standards follow long linked and
  reverse-linked chains until a record repeats. A recurring mask alone no
  longer truncates the result, while the requested merge depth for ordinary
  field values remains separate. Reading a record alone or in a batch,
  cached or live, produces consistent standards; changes to distant
  contributing records refresh the affected search documents. Localized
  fallbacks and asset attribution remain correct across masks. Existing
  records receive these corrections through the automatic full re-index.
  [4a26c76c3]

* **A category that sat at the top of a polyhierarchy no longer turns into a
  "deferred object" when the objecttype is switched to a single hierarchy**: a
  polyhierarchical objecttype lets a record name the virtual topmost entry as
  its parent, which is how it is marked top-level. That parent was stored as a
  real parent reference, and a single hierarchy has no virtual topmost entry —
  so after the switch the record hung under a parent that cannot be resolved,
  shown as `#0` in its path and as a deferred object in the parent field. Where
  the record also had a real parent, the virtual one came first and hid it, so
  the record disappeared from the branch it belonged to. The virtual topmost
  entry is now ignored while the objecttype is a single hierarchy: such a
  record is top-level, and one that had a real parent as well keeps that
  parent. Nothing is deleted — switching the objecttype back to a
  polyhierarchy restores the virtual topmost entry. [e86f31f8a]

* **An `eas/rput` from a public source is no longer refused by it**: the
  HEAD/GET check identified fylr to the remote, but the download that followed
  went out with Go's default `User-Agent`. Public sources refuse that —
  Wikimedia answers `403` to it — so an rput passed the check and then failed
  to fetch the file. Such a source also rate-limits a client that fetches many
  files at once, answering `429 Too Many Requests`, and that was treated as a
  final answer: the upload was refused, or the file was stored as `error`. In
  both cases the message the user saw was the source's, which reads like a
  fylr problem and is not one. The download now sends the same `User-Agent`
  the check does, and an answer that means "ask again later" (`429`, `502`,
  `503`, `504` — as opposed to a `403` or a `404`) is told apart from a final
  one: the check inside the request asks again up to twice, a few seconds
  apart, and the download in the file worker hands the job back to the queue
  for the delay the source asked for in its `Retry-After`, leaving the file
  pending instead of failed. A job that keeps being turned away this way for
  an hour is given up on, so an unreachable source cannot hold it in the queue
  forever. [09e32c1f6a]

* **A reindex no longer breaks on objects with a very long version
  history**: an index job takes 100 objects at a time and loads every
  version of each of them, so its real cost is the sum of their histories.
  On an instance where an external script had produced records with
  100.000+ versions, one job pulled 10 million rows and built an SQL list
  postgres refuses to parse — the job died with `invalid memory alloc
  request size 1073741824`, and the objects in it were then missing from
  the search index while the status page still reported nothing
  unindexed. Long lists are now passed to the database as a single bound
  value instead of being written into the statement, and an index job is
  capped by version rows as well as by object count, which also takes the
  memory such a reindex needs from 10.8 GB down to 3.1 GB. Instances
  whose objects have a handful of versions are unaffected. A single
  object with a history in the millions still produces an index document
  too large for opensearch to accept; it is reported as an index error on
  that object. [07a0ddcb5e]

* **A plugin installed by hand survives a plugin of the same name on disk**:
  when a plugin arrives from both sides at a start — a directory listed in
  `fylr.plugin.paths` and an installation somebody made through the plugin
  manager — the installation is meant to win and the copy on disk to be
  ignored. It was logged as such but not carried out, so the same plugin was
  written twice. That normally passed unnoticed, since the installed one was
  written last, but not when its storage location happened to be unavailable
  at that moment: fylr leaves such a plugin untouched on purpose until its
  storage is back, and with the duplicate present the copy on disk was written
  over it instead. The installation was then gone for good — the plugin came
  back as an on-disk one, without the ZIP or the URL it was installed from.
  [d631547f6]

* **A mapping still saves when a plugin recipe loses a parameter**: a plugin
  can build its recipe parameters from its own configuration — the AI Metadata
  plugin turns every row of its variables table into one — so removing such a
  row leaves every mapping, objecttype and pool that stored a value for it with
  a parameter the recipe no longer knows. The settings form cannot show that
  parameter, but it travelled back with the rest of the configuration on save,
  and the save was refused with *Unsupported param value ... for type
  `<unknown>`*. Nothing in the interface could clear the leftover, so the
  mapping could not be saved at all until the variable was created again. Such
  a value is dropped when the configuration is saved now — it addresses nothing
  — and everything else is stored as before. A parameter is only dropped once
  the plugin has actually delivered its recipe definition, so a plugin that is
  briefly unreachable cannot cost a stored configuration. Configurations passed
  with a single request — a per-url override on `/api/v1/eas`, a collection's
  mapping run — still report an unknown parameter as an error. [eed0d7ca7]

* **The /inspect Pages previews render again**: the Pages section of `/inspect`
  previews every login/registration page and every notification email against
  sample data, each in an iframe of its own. Two of them had stopped rendering
  and answered with an error instead: the registration page, and the
  collection-share email. The object list in the workflow notification emails
  (reject, resolve) was missing from their preview as well. The previews are
  now covered by a test that opens every page of the inspect navigation and
  every page and email preview, once per sample-data set. [ccbeda28c]

* **A plugin the license stops permitting keeps its configuration**: a plugin
  can be force-disabled while the administrator has it enabled — the license no
  longer grants it, or its ZIP has not arrived. Its base config was hidden with
  it, so the plugin manager offered no settings for a plugin nobody had
  switched off, its stored values looked deleted, and saving them was answered
  with 200 and dropped silently. Base config now follows the stored "enabled"
  flag: a plugin the administrator disabled stays hidden as before, while a
  blocked one keeps its settings section, its labels and its saves. The plugin
  management API reports the stored flag in `enabled` and names the reason the
  plugin cannot run in `state` (`not_licensed` beside the existing
  `not_installed`), so saving a plugin row can no longer write the
  force-disabling into the database — before, a plugin stayed off after its
  license or its source came back. Enabling a plugin the license does not grant
  is still refused; only saving the settings of an already-enabled one is not.
  (13509d069)

* **The marketplace catalog's `name_long` is now `repo_name`**: the field
  carries the repository a plugin is published from, not a long name for the
  plugin. The marketplace is new in this release, so no instance ever received
  the old key. (13509d069)

* **A migration keeps the upload settings of a collection**: after a migration
  from easydb 5, sharing a collection could fail with `Pool required for ...`,
  and sometimes the upload settings of the collection were gone altogether —
  the pool they used could not be resolved on the source anymore, and it was
  dropped without a word. Every pool the settings need but cannot get from the
  source is replaced by the standard pool now, and the backup log names each
  collection, so a proper pool can be set after the migration. Only the pool
  that is really missing is filled in: settings of an objecttype without pool
  management stay without a pool of their own, while the objects linked on
  upload get one as soon as their objecttype manages pools. Collections
  migrated earlier keep the settings they were restored with; they can be set
  again by hand. [e0dc73b97]

* **A deleted pool no longer takes the collections down with it**: deleting a
  pool that a collection used for the objects linked on upload left the pool
  in the upload settings of that collection, and reading collections answered
  a server error for every user afterwards. The setting that lost its pool is
  dropped from the collection instead and named in the log, so the pool can be
  set again. [e0dc73b97]

* **A storage location with `allow_redirect` delivers files directly again**:
  since version 6.18.0 every download was copied through **fylr** no matter
  how the option was set, so all asset traffic of an S3 location took the
  detour over the server instead of coming straight from the object storage —
  most noticeable with large files and video streaming. Downloads from an S3
  location with `allow_redirect` answer with a redirect to a signed storage
  URL again, and that URL now carries the file name **fylr** would have sent,
  so a downloaded file still arrives under its proper name. The option only
  ever applied to S3: a file location's signed URLs address **fylr**'s
  internal listener, and Azure cannot carry the file name, so both of them
  keep delivering the bytes themselves. [819a6f2c7]

* **Editing a data language code can no longer orphan multilingual field
  values**: renaming an existing database language in the base configuration
  (for example `de-DE` to `de-CH`) left every value stored under the old code
  behind — invisible in the editor, while mandatory-field validation blocked
  further saves because the field looked empty for the active language. The
  language code of a saved data language is read-only now; adding a language
  and removing one still work. Removing a language keeps its values in the
  database, and the re-index confirmation says so: they reappear once the
  language is added again. [eae454e3b]

* **Search no longer intermittently loses an object's latest index update**:
  parallel index workers could overwrite a freshly indexed document with one
  built from an older database snapshot — whichever write reached the search
  engine last won, and nothing repaired the loss. The affected object then
  failed index-side filters (tag sets, collection contents, OAI-PMH sets)
  until some later save re-indexed it, visible as sporadically incomplete
  search results and flaky CI polls. Every index write now carries a
  monotonic version and the search engine rejects the stale write.
  [2c327bd3a]

* **Changing a field's full-text option in a mask now offers the re-index it
  needs**: as long as *expert search* or *facet* stayed enabled for the field,
  saving the data model reported nothing to do, so the changed option had no
  effect on any record already stored — a newly enabled field remained
  unfindable in the full-text search, and a disabled one kept matching, until
  an unrelated full re-index happened to rebuild the index. Committing such a
  change now asks for the re-index the way every other index-relevant data
  model change does, and it can still be skipped. [66d3cff93]

* **A url plugin whose source reports an unstable checksum no longer updates
  in a loop**: a plugin's checksum is the source's etag, and a CDN may answer
  two requests from two replicas whose etags differ for byte-identical
  content (GitHub Pages derives them per backend). fylr probes with one
  request and downloads with another, and required both to agree — so an
  affected plugin logged "has a new checksum, will be updated", failed the
  download as a checksum mismatch and retried on every poll, indefinitely.
  The checksum is now treated as what it is, a hint that something *may*
  have changed: the downloaded bytes decide, compared by hash against the
  stored zip. Identical content installs nothing and records the checksum
  the source actually answered, and checksums proven to describe the
  installed zip are remembered, so a flapping source falls silent after one
  download per value. [c763e3bc1]

* **The `?login` share-link flag asks for credentials again**: a collection
  share link for a specific user or group appends `?login`, meaning the
  recipient must authenticate as that user. A browser holding a "Stay logged
  in" session ignored the flag and silently re-logged its stored user in;
  the login form now renders. The stay-logged-in session itself stays valid
  for tabs opened without the flag. [bcc568bf2]

* **Cross-server share links no longer log in twice**: opening a `?login`
  share link through a hosted web frontend (`?server=`) asked for credentials
  a second time after a successful login and left `?login=` stuck in the
  address bar — the web frontend tested the flag's value instead of its
  presence, the mirror image of the bug above. The flag is now forwarded to
  the login and stripped from the post-login redirect, so one login
  suffices. (webfrontend [4d015cd72])

* **A share link no longer asks readers who are already logged in**: with the
  two fixes above, `?login` insisted on the login form even when the recipient
  held a "Stay logged in" session and could already read the shared
  collection — a password prompt for something they were free to open. The
  authorize endpoint now checks that case: if the session's user may read the
  collection the link points at, they go straight in; everyone else — no
  session, a session from another browser, or no read right on that
  collection — still gets the form, so a link shared with a specific user
  keeps asking anyone else to identify themselves. Rights inherited from a
  parent collection count, and the check is skipped entirely when
  "Stay logged in" is switched off. [409229016]

* **A file's versions come out in a stable order**: the children of a file
  were read from the database unordered, so wherever they are flattened into
  a sequence — the CSV `file[N]` columns, the XML version elements — the
  order followed the query plan of the moment and could differ between two
  exports of the same data. They are now sorted with the original first, then
  by version name. The JSON API is unaffected: it keys the versions by name.
  [f5e42a3ce]

* **An unreachable storage location no longer disables plugins**: the plugin
  sync used to disable any plugin whose content failed to load — including
  when the storage location itself (e.g. an S3 outage) was the problem —
  and wiped its manifest state. Storage outages now leave the affected
  plugins' database rows untouched until the location returns; genuine
  content errors still disable. [2130eee87]

* **Cross-server /inspect logins no longer loop**: the OAuth callback hands
  the token to the browser in the URL fragment (stripped immediately after
  arrival, never sent to a server); previously a browser that had never run
  the inspect pages bounced back to the login. A credentialed deep link
  (`user:pass@host`) also no longer aborts the web app's boot script.
  [8259beff9]

* **A broken plugin release no longer piles up stored files, and a
  settings-save no longer masquerades as a plugin update**: a failed automatic
  plugin update stored its downloaded zip before validating it and never
  removed it — a plugin whose URL served a broken release re-downloaded every
  10 seconds and left one orphaned file per attempt. The updater now deletes
  the zip of a failed attempt and the superseded zip after a successful
  update, and keeps retrying a failed update every 10 seconds under every
  update policy, so a repaired release is picked up within seconds. The
  plugin timestamps now have a fixed meaning: *Updated At* moves only when
  the stored plugin content actually changed — saving settings (*Active*,
  the update policy) no longer touches it — and *Last Checked At* counts
  only completed source checks. [7ce1f0e0e]

* **The marketplace install URL of the Connector plugin was broken**: the
  plugin sheet sweep had taken a `<repo>` placeholder from a workflow comment
  as the install artifact, so installing `fylr-plugin-connector` from the
  marketplace failed. The catalog now carries the real, live URL.
  [a531c3d98]

* **Plugin callbacks see the same IP-filtered groups as the user who triggered
  them**: a group whose visibility is restricted to an IP range was evaluated
  against the address the callback connected from — the fylr server's own —
  instead of the address of the client whose call triggered the callback.
  Inside a callback a user therefore gained the groups allowlisted for internal
  ranges and lost the groups tied to their own subnet, so a plugin reading
  `/user/session` or acting through the callback token saw a different
  permission set than the user it was acting as. The triggering client's
  address now travels with the token fylr mints for the callback — a credential
  that exists only for that callback and is revoked with it — so it applies for
  as long as the callback may run, and to the callbacks a callback triggers in
  turn. Requests a client sends directly are unchanged: they are still
  evaluated against the address they arrive from. No configuration or database
  change is required. [9debcd25e] [ba3d96fcc6] [bdd48a4160]

* **SAML Single Logout works with IdPs that require signed logout messages**
  (Shibboleth's default): the Redirect-binding `LogoutRequest` fylr sends on
  logout now carries the query-string signature (`SigAlg`/`Signature`) the
  binding defines, so the IdP actually terminates its session and the next
  login asks for credentials again instead of silently signing the user back
  in. fylr also answers an IdP-initiated logout with a signed `LogoutResponse`
  (previously the IdP's logout flow was left unfinished), falls back to the
  POST binding for IdPs that only advertise a POST `SingleLogoutService`
  instead of quietly skipping the IdP logout, and verifies the signature of
  incoming signed logout messages — a `LogoutRequest` that fails verification
  is refused without ending the session. Unsigned incoming messages remain
  accepted. [745d1e38b]

* **Field type changes are validated the same way with and without data**: a
  type change on a column holding no values was previously accepted no matter
  what it changed into (for example a plugin custom type into a plain text
  field). A datamodel version created that way is rejected by another instance
  that does hold data in the column, which blocked the objectstore
  synchronization between the instances. Type changes are now checked against
  the supported-conversion matrix regardless of data, both when saving the
  development datamodel (HEAD) and on commit, so the error appears at the save
  that introduces the change and a HEAD that saves cleanly also commits
  cleanly. Columns that are not committed yet can still take any type. Note:
  an already saved, uncommitted HEAD containing a type change that was only
  legal under the old rule is rejected on its next save or commit until the
  field's type is reverted. The `TypeChangeUnsupported` message also no longer
  renders a stray quote after the type name. [1bb650efc]

* **Collection upload with metadata mapping no longer deadlocks on SQLite**:
  Uploading a file into a collection whose mapping creates objects
  (`create_object`, WebDAV/hotfolder imports) left the file stuck in status
  "processing" on SQLite until the request failed after a minute with
  `FileMetadataNotReady`: the request held the database's single write lock
  while waiting for file metadata that the file workers could not commit
  without that same lock. The metadata wait now happens before the write
  transaction opens — and only when a mapping is configured; a file whose
  processing outlasts the wait no longer fails the upload, the mapping
  degrades like before, on Postgres too. [2011b1984]

* **A broken plugin download no longer prevents the server from starting**: a
  url-installed plugin whose source could not be read at startup (network
  down, rate limit, 404, broken zip) failed the whole initialization and left
  the server in a restart loop until the url worked again. Such a plugin is
  now skipped with an error in the log, an already installed plugin keeps its
  row and configuration, and the plugin updater fetches the zip once the
  source is reachable again. The download error names the HTTP status
  instead of reporting `not a valid zip file` for an error page.
  [dbcd68ad1]

* **Managing a url-installed plugin no longer re-downloads it or loses a
  concurrent change**: enabling, disabling or changing the update policy of a
  url-installed plugin re-downloaded its zip on every save and left the
  previous copy behind as an orphaned file; an enable/disable saved while the
  plugin updater was in the middle of a long download could be silently
  reverted; and a purge could return before the configured plugins were
  re-installed. The stored zip is now reused unless the url changed or the
  update policy asks for a re-fetch, the updater re-reads the flags it does
  not own before saving, and purge waits for the plugin reconciliation to
  finish. [dbcd68ad1]

* **SQLite purge removes the write-ahead files**: purging deleted only the
  database file; in WAL mode the previous instance's `-wal`/`-shm` state
  stayed behind and leaked into the database recreated at the same path.
  [dbcd68ad1]

* **Listing events sorted by a field works again**: `GET /event/list` failed
  with a generic server error whenever `sort` named a field without an
  explicit `.ASC` or `.DESC` order, for example `sort=timestamp`. Such a sort
  is ascending again, as documented. [35875b971]

* **Video variants with strong color edits produce again**: producing a video
  variant that combines a strong saturation with a hue rotation failed with a
  `FILE_PRODUCE_ERROR` ("Numerical result out of range") for about 14% of the
  allowed saturation/hue range, regardless of the target format — first
  reported for MOV variants. The color correction now applies saturation and
  hue as separate, float-precision filter stages, which also brings the
  encoded result even closer to the editor preview. [ad91e66c8]

* **An object without a file no longer counts as the smallest file**: sorting
  a search by file size in groups (`number_groups`) put objects that have no
  file at all into the group of the smallest files, and a `fields` entry with
  mode `min`, `max`, `avg` or `sum` reported `0` for them instead of no value
  — so they were listed as, for example, "< 10 KB". A missing value stays
  missing in both places now: those objects form their own group after the
  last one, which sorts last when the order is ascending. [8af4221004]

* **A plugin keeps working after its unpacked files are cleaned up**: the
  execserver unpacks a plugin into its temp directory and removes it there
  again once it has aged out. When such a removal only got half way — the
  unpacked files gone, the directory left behind — the plugin still counted as
  installed, and every job it ran failed with `can't open file
  .../server/main.py` until the server was restarted. Saving a record through
  a plugin that hooks into it answered `"plugin: ..." caused an error during
  save` for as long as that lasted. A plugin whose files are missing is
  unpacked again now, a half-finished removal is retried, and a plugin that is
  in use no longer ages out from under a running job. [9c544586a]

* **The inspect index check no longer answers for the selected user**: the
  object list of `/inspect` counts the index documents of every object, and
  the user its user select picks (`?who=`) was applied to that count. With
  root selected no object reached the number of masks of its objecttype, so
  the whole database read as *partially found*; with a user without rights
  every object came back as *not found READ* — the state a monitoring on that
  page alarms on. Whether an index document exists is not a rights question,
  and the check answers from the index itself now, the way it already did
  with no user selected. [32f772df9]

* **The index check of `/inspect` counts the masks an object is really indexed
  under**: it called an object *found* only when the read index held a document
  for every mask of its objecttype, which is not the set the indexer writes. A
  mask behind a mask filter renders only the objects its tags select, and a mask
  that is not a standard mask of the object's pool gets no document at all — both
  are configuration, and both made every object of the objecttype read as
  *partially found* for good. That noise hid the real gaps it was meant to show,
  and producing it cost a search per 100 objects: on a database of 14000 objects
  a single deviating one took 22 searches and one percent of them 384. The
  expectation now comes from the masks the indexer actually writes, and the
  documents are counted with one aggregation per objecttype instead of a
  recursive split, so *partially found* and *not found* name an index error and
  nothing else. The list also takes only `all` or nothing for its `index`
  parameter now — any other value used to be accepted and silently counted
  everything, including the filter values of the per-objecttype list, which
  belong there and not here. [87900f14c]

* **ZIP listings report the real modification time, and directories report one
  too**: a ZIP entry carries two timestamps — a legacy MS-DOS field, which is
  local wall clock with no timezone and two-second granularity, and an extended
  field holding a real UTC instant. The directory listing of a ZIP served
  through `/api/eas/download` read the legacy field and labelled it `Z`, so an
  archive built outside UTC reported every `mod_time` shifted by its author's
  offset and rounded up to an even second. The extended field is used where the
  archive carries one. Directory entries carry timestamps as well and now
  report a `mod_time` instead of omitting it; `size` stays omitted for them,
  and `name`, `path`, `is_dir` and the set of entries are unchanged. Clients
  that store or compare `mod_time` from a ZIP listing will see the corrected
  values. [b52fe9712]

* **A failed file checksum names its cause again**: when reading a file's bytes
  failed, the checksum worker built its error message with a placeholder
  missing, so the underlying error was dropped from the text and replaced by
  `%!(EXTRA ...)`. The message carries the cause again. [b52fe9712]

* **An execserver fylr cannot reach no longer stalls the server**: when none of
  the configured `fylr.execserver.addresses` accepted a connection — a wrong
  port, or the execservers simply not up yet — every job first waited out
  `connectTimeoutSec` (120 seconds) before it was requeued. The plugins' dynamic
  recipes run one such job each, one after the other, while the server's cache
  is loading, so a startup and every later cache reload — the one after a
  re-index switches the index, for instance — stood still for minutes and
  answered 503 or nothing at all. A job whose execservers are all down is
  requeued immediately now, while an execserver that is merely still starting
  keeps the full `connectTimeoutSec` window to connect. fylr starts and serves
  without any execserver and picks them up as they appear; a warning names the
  configured addresses and this fylr's own execserver listener, since a
  mismatch between the two is the usual cause. [e9b142d33]

* **A read-only or deleted default location says so, instead of "no location
  configured"**: an upload into an instance whose default location for
  `originals` is read-only — or whose configured location no longer exists —
  failed with *NewLocationKey: No location configured for "originals"*, which
  sent whoever read it looking for a setting that was in fact set. The wording
  was not the whole of it: the `location_defaults` mapping stopped at the first
  role whose location it could not use, so the roles behind it — `versions` and
  `backups` — were left without a location as well, and backups on such an
  instance failed for the same invisible reason. Every role is mapped
  independently now, and the error names the cause: *The location configured
  for "originals" cannot be used: The location "..." is read only and cannot be
  configured as default location.* Configuring a read-only location as a
  default is still refused, as before. Any upload runs into this, a plugin zip
  included — everything without a version name is stored in the `originals`
  role. [92ed902bb]

* **A storage location that fails to connect at startup is retried, instead of
  staying broken until a restart**: the configured locations were connected
  once while fylr started, and a failure there was logged and left at that —
  nothing ever tried again except an operator saving the location through the
  API. A location that happened to be unreachable at that moment therefore kept
  its status `error` for the whole life of the instance, and every write to it
  failed with an error that named the symptom and arrived long after the event
  that caused it. That is not a rare race: an object store, or the credentials
  for it, becoming available moments after fylr does is enough, and a fresh
  install of the fylr Helm chart runs into it every time — the bundled minio
  creates its bucket, its policy and the user fylr authenticates as in
  post-install hooks, so fylr wins the start and loses the connect, and the
  instance cannot store a single file until somebody restarts it. Such a
  location is retried in the background now, every 5 to 30 seconds for as long
  as it stays broken, and the recovery is logged when it connects; only a new
  error is logged on the way, so a location that is misconfigured for good does
  not fill the log with the same line. Two things came with it: a location that
  reconnects no longer keeps the message of its last failure in `status_msg`,
  and the error a failed write returns names the cause instead of the status
  alone — *Location "s3"[1] has status "error" but needs to be in "connected":
  Cannot access bucket: ...*. Where an operator sees the state is unchanged and
  needed nothing: the Location Manager's status column and location form, and
  `/inspect/system/locations/`. [30aa65711]

* **The file-history janitor no longer skips versions saved moments before a
  run**: the cutoff for `keep_days_history_versions` was truncated to the full
  second while version timestamps keep sub-second precision, so with a keep
  window of zero days a version saved in the same second as a janitor run was
  passed over and only cleaned up by a later run. [9dd26c3e0]

* **Reindex counts as done only when the new index is searchable**: the
  index switch published before the last bulk writes were flushed and
  refreshed, so a client that polled `total_not_indexed` or the ready status
  and searched immediately could hit the freshly switched index up to a
  refresh interval (~1 s) before the reindexed documents were findable in
  it. The switch now waits for every in-flight index batch and refreshes the
  promoted index before it becomes visible. [61fe9d02be]

* **A failed request no longer crashes while its error is rendered**: when a
  request failed before the server's cache was loaded, translating the error
  message into the user's language ran on a context carrying neither a session
  nor a base configuration, and reading the missing configuration panicked the
  handler. The language preferences fall back to the default configuration now,
  and a request whose client has already hung up skips the error rendering
  altogether — there is nobody left to read it. That is the case this was
  reported for: a proxy in front of fylr aborts requests that queue behind a
  cache reload, and each aborted one left a stack trace in the log. No request
  answered a client differently because of it, and no process died — the HTTP
  server catches a panic per connection — but a single reload could fill the
  log with traces. [3389aa5b78]

* **A `--set` or environment override of a path setting resolves against the
  work dir again**: a relative filesystem path in the configuration is made
  absolute against a base directory chosen by where the value was set — the
  work dir for `--set` and the environment, the config file's own directory
  for a value read from a `-c` file, the executable's directory for a built-in
  default. When a config file and an override set the same key, both were
  recorded, under differently spelled keys, and the base directory was taken
  from whichever of the two came up first — so the same command resolved the
  path against the work dir on one start and against the config file's
  directory on the next, while the value itself always came from the override.
  The override now decides the base directory as well as the value. This
  affects every path setting that can be overridden, among them
  `fylr.tempDir`, `fylr.services.execserver.tempDir`, `fylr.licenseFile`,
  `fylr.resources`, `fylr.plugin.paths`,
  `fylr.services.backend.inspect.backup.path` and a sqlite `fylr.db.dsn`.
  A file storage location's `dir` is unaffected: it is resolved against the
  executable's directory in every case. [db59f39598]

* **The topology page no longer reports every file being produced as a stalled
  queue item**: `/inspect/system/topology` marks a claimed file-queue item
  stalled once no fylr has touched it for fifteen minutes, which says its
  claiming server died and left the work behind. It was instead comparing
  against the current moment, so every item the file dispatcher was legitimately
  working on counted — the page carried "file queue: N claimed item(s) stalled"
  for as long as anything was in production, with N the number of files actually
  being converted. The dispatcher itself was never affected and requeued the
  right items throughout; the count and the requeue rule now come from one place.
  The queue figure on the page was always correct. [5db559d5d3]

* **A watermark sized in percent keeps that percentage in every rendition**: a
  pool or objecttype watermark configured with a percentage — `50%` — sizes
  itself against the version it is placed on, so it should cover the same
  share of a thumbnail and of a large preview. It did in the small versions
  and shrank away in the large ones: the watermark image was only ever scaled
  down, never up, so once a version grew past the watermark's own pixel size
  the watermark stopped growing with it. The same 50% setting produced half of
  a 250px preview and a fifth of a 2000px one. It is now scaled up as well,
  which is also what the `50%x50%` form always did. Pixel sizes (`640x480`)
  are honoured the same way instead of capping at the watermark image's own
  size. Existing renditions keep the size they were produced with — resync the
  affected files to rebuild them. [46ed8228ca]

* **A fylr that starts before its execservers are reachable no longer hands
  them an address they cannot use**: fylr works out at startup which of its
  own addresses an execserver reaches it on, by asking the kernel what it
  would send from towards `fylr.execserver.addresses`. Where fylr and its
  execservers start together — a Kubernetes deployment, a compose stack — that
  name does not always resolve yet, and fylr then fell back to `localhost`.
  The first execserver to connect corrects it, and a job's pipes, its progress
  URL and the plugin transaction surface all follow — but the signed URLs a
  storage location hands out for the source file did not, because the location
  had already been built with the address of that moment. Such a fylr looked
  healthy and failed every file it was given: the jobs ran and the pipes
  worked, only no execserver could fetch anything to convert. Signed file URLs
  now carry the address in use when they are minted, the startup resolution
  waits up to ten seconds for the execserver name instead of giving up on the
  first attempt (and says so in the startup notices if it never resolves), and
  `/inspect` shows the callback address actually in use rather than the one
  predicted at startup. [26886b5dbb]

* **A version that can never be produced is shown as failed instead of going
  missing**: a version whose source version *failed* is recorded as failed, so
  a client polling for it reaches a terminal state. A version whose source
  version is never scheduled at all — because the produce
  configuration only produces it for other formats, or because a recipe
  decided against it — was skipped in silence instead, and neither the API nor
  the file's version list gave any sign that it had been configured. Both dead
  ends look the same from outside now, and the failure names the source
  version that is missing. A watermark version is unaffected: it is skipped on
  its own terms when the object carries neither watermark nor caption.
  [2ea62b3006]

* **Custom data with the same content is one entry, whatever expiry it
  carries**: a custom data entry which brings no `_uuid` of its own is
  identified by the MD5 of its data, and the custom data type updater writes a
  fresh `_expires_at` into that data on every run. Entries with identical
  content therefore hashed differently and piled up as duplicates which the
  de-duplication could never merge. The expiry is left out of that MD5 now.
  `_expires_at` stays part of the custom data and is returned like every other
  key of it — only the identity of the entry no longer depends on it. Existing
  entries keep their old UUID until the updater next touches them, so the
  duplicates merge over one expiry cycle rather than in one step at the
  upgrade. [80fe876940]

* **`GET /task/modules` names and explains every module and every parameter,
  in every language**: the localisation of the task modules had been moved
  into the server's own sheet, but in the frontend's key notation, which the
  endpoint does not read — it compiles `task.module.<module>.displayname` and
  `.description`, `task.module.<module>.param.<param>.displayname` and
  `.description`, and `….option.<value>` for a select parameter. Thirty of
  those keys had no row at all, so the endpoint answered with the bare key
  (`task.module.metadata.displayname`) where a label belongs, while seventeen
  rows in the old notation were read by nobody. The keys the endpoint actually
  compiles are in place now: the four modules that had no name have one, every
  parameter has a description where not a single one had before, and the whole
  block is translated into all nine languages rather than German and English.
  [e0333754a4]

* **A loca key with a stray space around it no longer goes missing**: keys in
  a localisation CSV are trimmed as the file is read. Whitespace around a key
  is invisible while editing the sheet, and a key carrying it never matched
  the key the code looks up, so the raw loca key was rendered where its
  translation belongs. This affects the localisation shipped with a plugin —
  none of the CSVs delivered with fylr contains such a key. [b383c144b]

* **The `X-Fylr-Timer-…` headers report what each section took**: they were
  measured from the moment a section started to the moment the response was
  written, so every nested section came back with the same figure — a search
  whose preparation took 11 milliseconds reported 54 seconds for it, next to
  three other sections showing the same number. Each section is measured on
  its own now. The new `X-Fylr-Timer-Elastic-Took` carries the time the search
  cluster itself reports for the query: next to the wall time of the call it
  tells an expensive query apart from time lost on the connection or in a
  queue. [64d4e7db3a]

* **A workflow webhook with the `after_commit_async` callback now sends the
  record's field values**: the payload carried the system fields — `_id`,
  `_version`, the parent — while every own field arrived empty, so a receiver
  reading the values out of it saw nothing and had to fetch the record back
  from fylr to get them. Which values arrived depended on the `format` the
  save that triggered the webhook was asked for, something nobody picks with a
  webhook in mind: `standard` and `long` filled them in, while `short` — what
  the file and metadata upload paths use — left them out. The records are now
  loaded for the format the payload itself is rendered in, so the webhook
  carries the committed values whichever format the save asked for.
  [0a314e26b]

## Frontend

* **Plugin manager README tab**: an installed plugin's README tab is shown
  exactly when the server reports `manifest.has_readme`, loaded on demand
  from `GET /plugin/manage/{id}/readme`; plugins no longer deliver a README
  copy into their webfrontend. (2d2291eae) (fea904abe)

### Improved

* **File worker configuration**: recipe and parameter hints render the
  localized descriptions delivered by the server; plain-string descriptions
  from older servers display unchanged. (14e6972c3)

### Fixed

* **No access token in the event stream URL**: the web frontend opened
  `/api/v1/event/stream` with the token as a url parameter, where it was
  exposed to logs and browser history. It now passes the token in the
  handshake header against fylr 6.35 and newer; against older servers the
  previous behaviour is kept, so a frontend served from one host can still
  talk to an older fylr. (000983e40)

* **Login validity window shown again for LDAP, SSO and email users**: the user
  editor hid "login valid from" and "login valid to" for these user types and
  cleared them on save. Both fields are editable again for every user type;
  only the password fields stay hidden where fylr manages no password. The
  server-side half of the fix shipped in 6.34.1. (7a17a9f9b)

* **Search autocomplete picks up changed settings immediately**: completions
  are cached in the browser for five minutes, and the cached address did not
  change when the user changed their settings — after switching the search
  languages, a previously typed query replayed the old completions for up to
  five minutes. The request now carries the user's version, so saving settings
  discards the cached completions. (09f601c49)
