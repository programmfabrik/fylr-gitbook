# Release v6.35.1

{% hint style="warning" %}
**Not released yet.** These notes describe fixes for 6.35 that have not
shipped: there is no `v6.35.1` tag, no build and no Docker image. Contents and
wording can still change before the release.
{% endhint %}

## Important

* **Storage locations no longer redirect downloads.** The `allow_redirect` option is removed: fylr delivers every file itself, from S3 as well, as it did up to 6.34. In 6.35.0 the redirect cost the web frontend its thumbnails when the bucket had no CORS rule for the instance. A `fylr.yml` that still sets `allow_redirect` loads; the key only produces an unknown-key warning. The update removes the option from the database, so an instance on 6.35.1 cannot go back to 6.35.0. There is no re-index. → [Location Manager](https://docs.fylr.io/for-administrators/location-manager) [fde1048c7]

* **Where execservers call back is set with `callbackBackendOwnURL` and `callbackApiOwnURL`.** fylr works out the addresses on which an execserver and its plugins reach it. Where it cannot, with fylr in a container or behind NAT and the execserver on another machine, `fylr.execserver.callbackBackendOwnURL` sets the backend address and the new `fylr.execserver.callbackApiOwnURL` the API address handed to plugins, each as written. `callbackBackendInternalURL` and `callbackApiInternalURL` are ignored; when one of them names another address than the one in use, the startup log names the key and the value to set instead. In 6.35.0 an installation that named its host only in the `InternalURL` keys handed the execserver the container's address. → [Execserver on another Linux](https://docs.fylr.io/for-system-administrators/installation/linux-docker-compose/execserver-on-another-linux) [1e8b608f5]

* **The re-index 202 of `POST /api/v1/objecttype` and `POST /api/v1/pool` is answered with `confirm_reindex`.** The query parameter was called `confirmReindex`, which is no longer read. A script that sends a fixed `confirmReindex=yes` sends `confirm_reindex=yes` now; a client that repeats the button of the 202, like the web frontend, needs no change. See "Backup and restore with mask filters and standard masks" under **Fixed**. [6e1316363]

## fylr core

### Improved

#### OpenSearch: a user limited to the instance's own indices

fylr runs with an OpenSearch user whose rights cover only the instance's own indices, `<fylr.name>-<uuid>-…`, so several instances can share one OpenSearch without reaching each other's indices. Changing the database languages no longer needs the right to create an index outside these. When OpenSearch does not let fylr read the cluster settings, fylr keeps `fylr.elastic.maxMem` as configured and logs a warning at startup. → [OpenSearch user per instance](https://docs.fylr.io/for-system-administrators/installation#opensearch-user-per-instance) [926ebf7c9]

### Fixed

#### Backup and restore with mask filters and standard masks

A restore of a backup whose object types or pools have mask filters or standard masks no longer stops with `Error received: 202 Accepted:` at `basetype_objecttype` or `basetype_pool`, also into an instance that already holds records; the restore re-indexes at its end. A backup holds the mask filters of the object types again: since 6.11.0 it left them out, so a restore brought the object types back without them, and a backup made before 6.35.1 still lacks them. `POST /api/v1/objecttype` and `POST /api/v1/pool` save a mask change that affects no record without the re-index 202, and `confirm_reindex=skip` (with `system.root`) saves without queuing the re-index, for a client that re-indexes afterwards. [6e1316363]

#### Polyhierarchy: records below the virtual top level in the filter

A record of a polyhierarchical list that also hangs from the virtual top level is listed on the top level of the filter as well as below its other parent, and selecting it there finds the same records. In the API, a `linked_object` aggregation with `filter_parent` `null` or `0` returns such records on the top level. [cd3215840] [b319d616f]

#### Export: running an export no longer changes its saved search

An export whose search uses a subsearch no longer gets another copy of the not-deleted filter written into its saved search on every save and run, so the saved search no longer grows. A subsearch saved without `limit` keeps having none, and an export saved without objecttypes keeps searching all of them, also those added to the datamodel later. [c95d356e4]

## Web frontend

### Fixed

* A guest no longer gets *Self update of "company" is not allowed* when the web frontend saves its settings, for example on opening a mask panel or switching the result view. Since 6.35.0 fylr lets a guest save only its frontend settings on its own user, and the web frontend sent the profile fields along wherever a group gave the guest the right to edit them. [8c9b50914]
* In the detail of a polyhierarchical record, *Virtual Top Level* among the parents reads like the other parents and no longer opens a quick view that calls it deleted, and a record with several parent paths shows one row per path. [b319d616f]
* The location manager no longer offers *Allow Redirect*, see **Important**. [ece870120]
