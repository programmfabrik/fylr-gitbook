## Server

### Important

* **Storage locations no longer redirect downloads.** The `allow_redirect` option is removed: fylr delivers every file itself, from S3 as well, as it did up to 6.34. In 6.35 the redirect cost the web frontend its thumbnails when the bucket had no CORS rule for the instance. A `fylr.yml` that still sets `allow_redirect` loads; the key only produces an unknown-key warning. → [Location Manager](https://docs.fylr.io/for-administrators/location-manager) [0a363df10]

* **File storage locations created through the API need an allowed directory.** A location of kind `file` can be created through `/api/v1/system/location` and the Location Manager, or moved to another directory there, only inside a directory listed in the new `fylr.yml` setting `fylr.locations.allowedDirs`, which is empty by default. Existing locations, and those configured under `db.init.locations`, keep working. → [fylr.example.yml](https://docs.fylr.io/for-system-administrators/configuration/fylr.example.yml) [6137804c4]

* **A workflow action of a plugin that is enabled but cannot run rejects the save.** When the license does not permit the plugin, its files have not arrived or it no longer provides the action, a save the workflow applies to fails with `400 TransitionActionUnavailable` naming the action, until the plugin can run again or the action is removed from the workflow. The action of a plugin that the admin switched off in the plugin manager, or removed, is skipped and logged. → [transition\_db\_pre\_save](https://docs.fylr.io/for-developers/plugin/callbacks/transition-db-pre-save#errors) [e1bf3a628] [907a87d54]

* **The backend listener needs the instance's backend secret.** Every request to the backend port (`fylr.services.backend.addr`) carries the backend secret, which fylr creates at setup and keeps in the database, in the `X-Fylr-Backend-Secret` header, or uses a URL fylr signed with it; `/`, `/healthz` and `/metrics` answer without it. The execserver jobs and the `/inspect` pages of the web frontend need no change. A script or monitoring that reads `/inspect` on the backend port reads it through the webapp with a root session or token instead. File jobs and backups that run while fylr is updated can fail once and need to be repeated. → [fylr.example.yml](https://docs.fylr.io/for-system-administrators/configuration/fylr.example.yml) [bce5c27d9] [3dbb764a1]

* **The quality of preview versions is set with `quality`.** The option `jpegquality` of the recipe `imageconverter:browserthumbs` is now called `quality` and also applies to WebP versions. The update renames it in the stored produce configuration. A produce configuration that still uses `jpegquality` afterwards, posted over the API or restored from a backup of an older instance, sets no quality: its versions use the encoder's default. See "Preview versions: the quality applies to WebP" under **Fixed**. → [Preview configuration](https://docs.fylr.io/for-administrators/readme/file-worker/preview-configuration) [cdfaa91f2]

* **`DELETE /api/v1/db/{objecttype}` without `delete_policy` deletes a record nothing links right away.** A record which no other record links and which has no reverse-linked or subordinate records is deleted at once, the answer is `200` with the policy `remove`; the `202` with the policy choice comes only when the deletion affects other records. A script that sends the request without `delete_policy` to see the choices first now deletes such records. → [Deleting Records](https://docs.fylr.io/for-users/asset-records-management/deleting-records#deleting-referenced-records) [e27f35218]

* **Where execservers call back is set with `callbackBackendOwnURL` and `callbackApiOwnURL`.** fylr works out the addresses on which an execserver and its plugins reach it. Where it cannot, with fylr in a container or behind NAT and the execserver on another machine, `fylr.execserver.callbackBackendOwnURL` sets the backend address and the new `fylr.execserver.callbackApiOwnURL` the API address handed to plugins, each as written. `callbackBackendInternalURL` and `callbackApiInternalURL` are ignored; when one of them names another address than the one in use, the startup log names the key and the value to set instead. → [Execserver on another Linux](https://docs.fylr.io/for-system-administrators/installation/linux-docker-compose/execserver-on-another-linux) [e0a3857e4]

* **The update runs a full, blocking re-index.** The filters of linked records and pools use a new index layout. Until the new index has switched in, the web frontend and the API answer `503`, apart from the login, `/api/v1/settings` and `/api/v1/system`; `/inspect/` stays available. On a copy with 495,000 records the re-index took 21 minutes. See "Filters of linked records and pools: faster on large instances" under **Improved**. → [Re-index](https://docs.fylr.io/for-system-administrators/inspect/system#re-index) [e8c71d466]

* **Many requests the server refuses answer a documented error code.** Across the API, a request with a body, parameter or value the server cannot take answers a typed code whose parameters name the field and the value, such as `400 RequestParseError`, `400 FieldValueInvalid`, `400 SearchValueInvalid`, `400 UrlParameterInvalid` or `404 ObjectNotFound`, instead of `400 ServerGeneric`, `400 DatabaseError` or a caught crash; the API documentation lists every code with its parameters. Requests the server accepts answer as before. A client that reads the text of a `ServerGeneric` error should read the code instead. See "Typed error codes" under **Fixed**. [5826ff075] [04885f63f]

* **Presetting record ids and dates on `POST /api/v1/db/{objecttype}` needs `system.root`, as does `skip_constraints`.** A create that presets `_system_object_id` or `<objecttype>._id`, also for a new reverse nested row and with `dry_run`, answers `403 ObjectPresetIdRequiresRootRight` for other users; a preset `_uuid` stays open to every user, and a link or parent deferred with `_allow_defer` by `_system_object_id` needs `system.root` as well, by `_uuid` not. A true `skip_constraints` answers `403 SystemRightRequired` for other users, as `skip_plugins` and `skip_events` do, so the *skip constraints* option of the web frontend's JSON importer works only for them. `_created` and `_last_modified` are taken only from a `system.root` user; for others the version is dated at the time of the save, also when a record read is sent back. Restores, migrations and imports that keep ids or dates run as a user with `system.root`. [2ade30898] [e472ea713] [833f04901] [942999c1d] [d4d90a336]

* **Saving a deleted record answers `404 ObjectNotFound` and leaves it deleted.** An update by `_id`, `lookup:_id` or the next `_version` of a record whose current version is deleted answers `404 ObjectNotFound` with the object `#<_system_object_id> (deleted)`, in single and in group mode. A script that updates records it finds by lookup has to leave deleted ones out; a record is restored with `DELETE /api/v1/db/{objecttype}` and `delete_policy=undelete`, which needs `system.trash_access`. [7447e544b]

* **Reverse nested records go through the workflow of their own object type.** `POST /api/v1/db/{objecttype}` checks the records it creates, changes or deletes through a reverse nested table, e.g. the images of an object, with the transitions of their object type: a reject answers `400 TransitionReject` naming the record, and a confirmation answers a second `202` after the owner's, whose token already carries the first one. Their tag, owner, e-mail and after-commit actions run; their plugin and `pre_save` webhook actions do not. A workflow that rejects inserts or deletions of such records now also applies when they are saved along with their owner. [437851874] [4496f89f9]

* **The caption of an object type takes only its own files fields.** `POST /api/v1/objecttype` answers `400 CaptionInvalid` for a caption key that names a files field of another object type, which no rendition reads, and for a files field in a nested table of an object type with pool management, whose records use the pool's caption. An object type that has such a key stored is refused on its next save until the key is removed from its caption. [956fcb1e8]

* **Search elements that cannot match answer `400`.** A text (`match`), `range` or geo element and a `date_range`, `linked_object` or geo aggregation on a boolean column answer `400 SearchFieldNotAllowed`, as does a boolean column in the `fields` of `/api/v1/suggest`; `in`, `sort`, `fields` and the term aggregations take boolean columns as before. A search element, sort or aggregation on a system field below a link or reverse field that the index does not hold, such as `_owner`, `_collections`, `_comment` or `_fulltext` of a linked record, answers `400 SearchFieldNotAllowed` too; these names still work in `include_fields`, `exclude_fields` and `fields`. Such elements never matched a record. [e6439df6b] [c99a0ec9f] [9a1a48c22] [59573b090] [8e90cd8ec]

* **OAI/PMH collection sets are the collections the harvesting user may read.** `set=collection:<id>` of a collection the harvesting user may not read answers `badArgument` "Unknown set", like a collection that does not exist, and the header of a harvested record names only the collections that are sets for that user, as `ListSets` lists them; system collections are no sets. A harvester needs read on every collection it harvests as a set. [5179836da]

* **`POST /api/v1/export/{exportId}` updates an export only for its owner or `system.root`.** An update of a stored export, also through `POST /api/v1/export` with the `_id` in the body, follows the rule of reading and deleting it: other users get `403 InsufficientRights`. The update keeps the stored owner, also when a `system.root` user saves it. [42b7aaa2f]

* **The JSON data file of an export follows `fields`.** With `fields` set, the JSON file holds only the listed columns of the record and of its nested and reverse nested records, like the CSV, XLSX and XML files. A linked record is written whole when its column or a field below it is listed, and the keys around the record (`_system_object_id`, `_format`, `_tags`, ...) stay. A consumer that reads other columns from such a JSON file needs them added to `fields`. [5b77ca6c5] [288af3ee2]

* **`custom_produce_config` is checked when it is set.** `POST /api/v1/eas/{fileId}`, `POST /api/v1/eas/put`, `POST /api/v1/eas/rput` and `POST /api/v1/eas/rput/bulk` check its values against the recipes of the file's class: a value a recipe refuses (`size` `abc`, `quality` 101, a `format` the recipe does not offer) answers `400` with its `RecipeParam...` code and nothing is stored, and `eas/rput/bulk` refuses the whole request. Such a value used to be accepted and to fail only when the version was produced. [22c86bddd]

* **Moving a record to another pool needs `link` and `unlink` from the pools' `_acl`.** A save of `POST /api/v1/db/{objecttype}` that moves a record needs `link` in the new pool and `unlink` in the old one, granted in a pool `_acl`; `link` and `unlink` granted in a collection `_acl` add records to the collection and remove them, and do not count for the move. `unlink` in `_generated_rights` of `GET /api/v1/db` and `POST /api/v1/db_info/update` comes from the pool `_acl` only. Users who moved records with collection grants alone get `403` and need the rights in the pools. [477ad24d8]

* **Pool saves: the owner of a new pool, and the fields sent next to `_acl`.** Creating a pool with `POST /api/v1/pool` whose `_owner` is not the saving user, also a group the user is a member of, needs `system.root`, as an owner change does; other users get `403 RightRequired`. An update that sends `_owner`, `_standard_masks`, `_transitions`, `_tags` or their `_private_` flags needs `bag_write`, also next to `_acl`. An update that sends only `_acl` and `_private_acl` (next to `_id`, `_version` or `lookup:_id`) keeps every other stored value, the watermark, the caption and the standard masks included; these used to be cleared. [afec93e55] [f489d4962]

* **Changing a grant's time window, a pool's `_private_acl` or a pool's parent checks the shared collections.** A save of the `_acl` of a pool, object type, tag or collection runs the check of the collections that share their records also when a grant only gets another `when` window, and `POST /api/v1/pool` runs it also when `_private_acl` changes or the pool moves to another parent, for the records of the pool and of the pools below it. Such a save can answer `202` with `allow_invalid_acl` for a caller with `bag_acl` on the collection, or `403 CollectionObjectInsufficientRights`, as other `_acl` changes do. Scripts that move pools or change grant windows must handle these answers. [49f58e796] [d05fdfaff]

* **`allow_invalid_acl` and `background_invalid_acl` act only on collections the caller has `bag_acl` on.** On `POST /api/v1/pool`, `POST /api/v1/objecttype`, `POST /api/v1/tags`, `POST` and `PUT /api/v1/user` and `POST /api/v1/right/{context}/presets`, `allow_invalid_acl=true` from a caller without `bag_acl` on a collection the save would flag answers `400 UrlParameterNotSupported` (param `allow_invalid_acl`) and saves nothing. `background_invalid_acl` is ignored for a caller without `bag_acl` on every checked collection, so the check runs in the request and answers its `202` or `403`. `system.root` has `bag_acl` on every collection. [aadd18e12] [f4ffb43d2] [b568ae00b] [4514e716b]

* **A grant in an `_acl` names a right preset of its own context and has no tagfilter next to the preset.** Every `_acl` save (records, pools, object types, tags, collections, users, groups) answers `400 RightPresetContextMismatch` for a record, object type or tag grant naming a collection preset, a collection grant naming an object preset and a pool grant naming any preset; user and group grants take both kinds. A grant that sends `_right_preset` together with a non-empty tagfilter answers `400 TagfilterWithPresetNotAllowed`; the empty lists a client sends back are accepted. Such grants already stored stay, and a save that does not send them succeeds; a request that sends one back is refused. [08528eca7] [074e899ea]

* **A workflow whose `set_tags` action names a deleted tag rejects the saves it applies to.** Such a save answers `400 TagNotFound` with the tag id and stores nothing; the action used to be skipped without notice, its valid tags included. Deleting a tag does not remove it from `set_tags` actions, so check the workflows of the tag manager, the pools and the object types for tags that no longer exist. [024c3cc88]

* **Archiving a user applies the pseudonymization of every group of the user.** The `_pseudonymization` of the system groups of the user's type (`system::easydb`, `system::all` and the others) and of the groups that claim the user by an `_auth_method_group_maps` rule now applies when the user is archived, as that of the assigned groups always did. Check these groups before archiving users: archiving cannot be undone. See "Users: archiving applies the settings of every group" under **Fixed**. [830bafb85]

* **`GET /api/v1/user/session` and `POST /api/v1/user/change_password` answer other error codes.** `GET /api/v1/user/session` without a token answers `401 UserRequired`, like every other operation; `401 InvalidToken`, which now names the token, comes only for a rejected token. `POST /api/v1/user/change_password` answers the password rules with `400 PasswordRequirementNotFulfilled` instead of `403`, with the configured hint as parameter, and its other refusals with `NoPassword`, `PasswordUnchanged`, `EmptyPassword`, `UserHasNoPassword` and `RequestParseError` instead of `400 ServerGeneric`. A client that tests for `InvalidToken` to find a missing session, or for the `403` of the password rules, must accept the new answers. [7bda012e7] [453e56a6f]

* **The OAuth2 password grant answers a wrong password and a login that is not allowed alike, and gives no token to a user who must change the password.** `POST /api/oauth2/token` with `grant_type=password` answers an unknown login, a wrong password and a user who is login-disabled, archived or outside `login_valid_from` / `login_valid_to` with the same `400 invalid_grant` "invalid credentials", as the login form shows one message for them; a locked account, an unconfirmed e-mail address and a license without user logins still name their reason. For a user with `require_password_change` it answers `400 invalid_grant` "a password change is required; sign in via the web interface"; tokens issued before stay valid. A client that told its users "login disabled" from this answer can no longer do so, and a script that logs in as a user who must change the password needs the password changed through the web login first. [569801d85] [934e9caa0]

* **A disk plugin added through the plugin manager must lie inside `plugin.paths`.** `PUT /api/v1/plugin/manage` with type `disk`, and `POST /api/v1/plugin/manage/{id}` with a new `path`, take only a directory inside one of the `plugin.paths` of `fylr.yml`, a relative path taken from the working directory and symbolic links resolved; any other path answers `400 PluginPathNotAllowed` before anything is read. Plugins already registered and the plugins of `fylr.yml` keep their paths. Add the directory to `plugin.paths` before registering a plugin from it. [3614a2169]

* **`POST /api/v1/config` refuses a select or string-list value that is none of its options.** Such a value answers `400 BaseConfigParse` naming the parameter, and nothing is stored; an unknown select value was stored as the first option, an unknown string-list entry as sent. A value stored at the same place is accepted when a client sends it back, so posting a section that was read keeps working after an update removed an option. Scripts that post base config values check them against the options of the `BaseConfig` schema. [1333c222d] [ab5f26dce]

### New

#### The license updates itself

fylr keeps its license current: every 6 hours, and right away when the option is switched on, it sends the installed license to the programmfabrik license server and installs a newer version of it, so a renewed or extended license reaches the instance without an upload. The option **Update the license automatically** in the base config's license management, on by default, switches it off, e.g. for an instance without outgoing internet access; `fylr.licenseServer` in `fylr.yml` sets the server, an empty value switches the update off for the installation. Every installed update is logged as a `LICENSE_AUTO_UPDATE` event. → [Automatic license updates](https://docs.fylr.io/license-management#automatic-license-updates) [01eb9eef6]

#### Plugins: an instance can be limited to marketplace plugins

With `plugin.sources: marketplace` in `fylr.yml` an instance runs only plugins from the marketplace catalog: the plugin manager installs no ZIP upload, disk path or other URL, and an installed plugin that was not checked against the catalog stays switched off until it is installed from the marketplace. Plugins configured in `fylr.yml` under `plugin.paths` and `plugin.urls` are always accepted; the default, `any`, keeps the current behaviour. In both modes, a plugin whose catalog entry lists a checksum is installed and updated only with a ZIP that matches it: a download that does not match is refused, the installed version keeps running, and the plugin manager says why. → [Marketplace plugins only](https://docs.fylr.io/for-administrators/plugin-manager#marketplace-plugins-only) [7c0e177f0]

### Improved

#### Inspect: favorites and the instance in the top bar

Any inspect page can be a favorite: a section, a single objecttype, user or file, a page with its query. The star next to the page's title adds it to the favorites, a bar under the top bar of every inspect page, where a favorite is dragged to its place, renamed by a double click and removed by the × it shows on hover; the browser remembers the favorites. The title of a sub page names its section and the rest in grey ("Objecttypes ot_b" instead of "Objecttype/ot_b"). The tiles of the home page are smaller. Name, version, database with its size, indexer and backends of the instance are in the top bar of every inspect page instead of a card on the home page; the API documentation takes the colors of the other pages. → [The home dashboard](https://docs.fylr.io/for-system-administrators/inspect#the-home-dashboard) [f072ae09f]

#### Command line: every flag also as an environment variable

Every flag of the `fylr` command line can also be given as the environment variable `FYLR_CLI_<FLAG>`, e.g. `--password` as `FYLR_CLI_PASSWORD` and `--client-secret` as `FYLR_CLI_CLIENT_SECRET`, which keeps passwords out of the process list; a flag on the command line takes precedence, and `fylr <command> --help` names the variable of each flag. Backups and restores started from `/inspect/migration`, database backups and *Restore DB* hand passwords and secrets to the programs they start that way. → [Backup](https://docs.fylr.io/for-system-administrators/migration/backup) [9823c0d92]

#### Placeholders for custom data types: IIIF, file names, captions

A field of a custom data type offers its standard as `%<object type>.<field>._standard%` and each sub field its plugin maps as `%<object type>.<field>.<sub field>%`, e.g. the URL of a weblink as `%foto.rights_link.url%`, which stays the URL when a link text is entered. They work wherever record values are replaced: the IIIF rights and required statement, the file names for download and export, captions and the record values in recipe parameters; *Show Replacements* of the file names lists them. A localized standard or sub field resolves in the language of the value, `%….de-DE%` names one language. → [IIIF placeholders](https://docs.fylr.io/for-administrators/readme/export-and-deep-links#iiif-placeholders) [947ede018]

#### Deleting records: the policy dialog only when there is a choice

Deleting a record that no other record references, and that has no reverse-linked or subordinate records, no longer opens the dialog "The record you are trying to delete is referenced in other records" after the confirmation: the record is deleted. *Create collection with records to be deleted* creates one collection with the records to be deleted and below it *Preventing the deletion* and *Affected by the deletion*, each only when it is not empty, instead of seven collections. → [Deleting Records](https://docs.fylr.io/for-users/asset-records-management/deleting-records#deleting-referenced-records) [e27f35218]

#### OpenSearch: a user limited to the instance's own indices

fylr runs with an OpenSearch user whose rights cover only the instance's own indices, `<fylr.name>-<uuid>-…`, so several instances can share one OpenSearch without reaching each other's indices. Changing the database languages no longer needs the right to create an index outside these. When OpenSearch does not let fylr read the cluster settings, fylr keeps `fylr.elastic.maxMem` as configured and logs a warning at startup. → [OpenSearch user per instance](https://docs.fylr.io/for-system-administrators/installation#opensearch-user-per-instance) [bc3cd20da]

#### Plugins: Python packages ship with the plugin

Plugins built with fylr-build-plugin 1.10.0 or newer bring the Python packages of their `python3` programs with all their dependencies, so nothing is installed on the instance. Compiled packages cannot ship and come from the fylr image, which now installs `numpy` explicitly beside `opencv-python`; a fylr installed from source needs `python3-numpy` for such plugins. → [Plugin Conventions and Standards](https://docs.fylr.io/for-developers/plugin/conventions#build) [044337398]

#### Search suggestions: the count of a word

In `/api/v1/suggest`, the `count` of a word suggestion is the number of records a token search for the word finds within the request's `objecttypes`, `pool_ids`, `fields` and search languages, each record counted once, so it matches the hits when the suggestion is chosen. [1a4a012ce]

#### Filters of linked records and pools: faster on large instances

The filters of linked records, of hierarchical lists and of pools no longer take longer the more linked records an instance holds: what they take follows the number of records the search finds. On a copy with 420,000 records the filters of a search over all of them take 88 ms instead of about 400 ms, over 48,000 records 7 ms instead of 230 ms, and over a few hundred 1 ms instead of 260 ms; a level of a hierarchical filter takes half the time. The filters no longer keep their data in the memory of OpenSearch, 135 MB less on that copy. The update runs a re-index, see **Important**. [e8c71d466]

#### API documentation: search fields, error codes and pages that load

The API documentation of an instance, on `/inspect/apidocs/` and in `GET /api/v1/system/openapi/spec.json`, lists the fields each search type accepts and whether `in`, `range`, `text` and `sort` take them: for `pool`, `collection`, `event`, `message`, `user`, `group` and `acl` from the code of these searches, for objects from the instance's datamodel. An error response names its codes in one `Error` schema, with `code` as an enum and the parameters of each code, instead of a `oneOf` of one schema per code, so a client generated from the spec gets one error type. The `BaseConfig` schema puts the parameters of a plugin's config under their sections, as `GET /api/v1/config` answers them, and the OAuth2 endpoints document every parameter, grant and error with the `OAuth2Error` they answer. The pages link component schemas and list each one once, so the page of `POST /api/v1/search` renders in about a second; it never finished loading before. A per-objecttype operation links to its generic one, and `?datamodel=0` shows any page, `spec.json` and the spec tree without the instance's datamodel. [55bf7208f] [709e3aba7] [d6320035b] [05f2bf376] [945fbf464] [22996d843] [3c6fdeff6] [04c0ecc7c]

### Fixed

#### Workflow e-mail recipients

Saving workflows no longer fails with "sqlpro.ExecTX: panic caught" when an e-mail action has an empty recipient row; the message names the workflow and the row instead. An e-mail address that is not yet a user can be added as a recipient ("… anlegen"): saving the workflow creates the e-mail user, in the tag manager as well as in pool and object type workflows. → [Tags & Workflows](https://docs.fylr.io/for-administrators/permissions/tags-and-workflows) [695ea9c56]

#### Base config: secrets kept when one value is set by path

Setting or removing a single value of a base config section through the API by its path (`POST` / `DELETE /api/v1/config/…/<section>/<parameter>`) keeps the passwords and keys stored in that section; they were replaced by their mask and had to be entered again. This covers plugin sections as well as e.g. the e-mail server and LDAP passwords. → [Secrets](https://docs.fylr.io/for-developers/plugin/manifest/base-config#secrets) [9ce9bcde5]

#### Base config: secrets stay with their table rows

Moving or removing rows of a table in a plugin's base config keeps each row's passwords and keys in its own row; the rows after a moved or removed row used to get the secrets of other rows. → [Secrets](https://docs.fylr.io/for-developers/plugin/manifest/base-config#secrets) [d5122f570]

#### Re-index: a failed run no longer blocks the instance

A blocking re-index that fails, for example because OpenSearch refuses to create the new index, lifts the block again; the web frontend and the API no longer answer `503` until fylr is restarted. The `REINDEX_ERROR` event and the answer of `POST /api/v1/system/reindex` name the reason. With OpenSearch 3 the most common one is a missing `-Dopensearch.xcontent.depth.max=10000` in `OPENSEARCH_JAVA_OPTS`. While a blocking re-index runs, file downloads keep working, so the maintenance page shows the logo and pages that embed fylr images keep them. → [Re-index](https://docs.fylr.io/for-system-administrators/inspect/system#re-index) [aba378956]

#### Plugin manifests

Keys of a plugin's `manifest.yml` that fylr read but did not apply work as documented: an exec argument of `type: int` passes its number instead of `0`, a custom data type updater without `update.batch_size` hands its program 100 records per call instead of none, and a system right parameter of type `eas-class-list` can be granted. A plugin whose `fas_config.produce_config` file is missing, or whose `db_pre_save` step has an unknown filter type, is invalid like one with a missing cookbook: it is refused on install and disabled at the next start. A system right parameter of a type a system right cannot store, such as `mask-select`, is ignored with a warning in the server log. → [Plugin manifest](https://docs.fylr.io/for-developers/plugin/manifest) [e1bf3a628]

#### Plugins: one plugin that fails to load no longer stops the others

A plugin whose JavaScript fails to load in the web frontend, because of a syntax error or an error while it starts, stops only itself; the browser console names it, and the plugins after it load as before. It used to stop every plugin loaded after it, so an instance with one such plugin could end up without any custom data types: the data model offered none, and their fields showed "plugin not loaded". Plugins without a dependency between them load in the order of their names; they loaded in reverse order. → [webfrontend](https://docs.fylr.io/for-developers/plugin/manifest#webfrontend) [019800b3b]
